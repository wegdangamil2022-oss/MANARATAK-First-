# تجهيز مرشح validation/staging للمراجعة

الحالة: **حزمة مراجعة قابلة للتوليد؛ تشغيل staging والترقية محجوبان**. هذه خطوة ضمن R14، بعد نطاق Linux الصناعي المثبت، وليست قبولًا رسميًا أو تصريح نشر. تستمر المراجعة في [PR34](https://github.com/wegdangamil2022-oss/MANARATAK-First-/pull/34) على الفرع الحالي دون دمج main.

## المرجع المعروف

المصدر التشخيصي المختار `aaf932e17c10e71d37d7f69a50dfe1c20e7c4b1b`، وتشغيل Actions39648892069 ناجح بست وظائف، بما فيها الإقلاع وCMS والتراجع الفعلي. تحفظ [الأدلة](../reviews/evidence/post28/aaf932e17c10e71d37d7f69a50dfe1c20e7c4b1b/r14-linux-rollback/evidence-index.json) بصماتها ومصدرها الأصلي. ليس هذا تجميد C2 النهائي؛ أي تغيير في مدخلات التطبيق يتطلب مرشحًا وأدلة جديدة. لا تُنسب هذه النتائج إلى SHA أداة التجهيز أو commit التوثيق اللاحق.

## ما جُهز في المستودع

- [خطة المراجعة](../../config/release/staging-review.json): Linux x64، Node22، PostgreSQL16، أصل HTTPS واحد للموقع وAdmin وAPI، عربية عامة، بيانات صناعية مستقلة ومزودون sandbox/stub فقط.
- أداة توليد محلية تتحقق من بصمات أدلة Linux وCI، وتطابق SHA، وعدم تغير مدخلات التطبيق عن المصدر المختار. لا تقرأ أسرار البيئة أو تتصل بقاعدة أو شبكة أو مزود أو أداة ترقية.
- توليد `review.json` و`api.env.reference` و`packet-index.json` خارج checkout وفي مجلد جديد فقط. القالب يشمل كل مفاتيح AppConfig الإلزامية الحالية؛ جميع التعيينات معلقة وفارغة عدا قيم النطاق المعروفة. لا يحتوي أسرارًا ولا يصلح للإقلاع كما هو.
- استدعاء ProductionReadinessValidator الفعلي على قيم المراجعة، لإظهار العوائق بدل اختلاق حالة جاهزة.

من جذر checkout نظيف، باستخدام Node22 والاعتمادات المثبتة:

```sh
node --import tsx scripts/release/prepare-staging-review.mjs /absolute/outside-checkout/new-staging-review
```

النتيجة المنتظرة `REVIEW_PREPARED_TARGET_AND_RUNTIME_BLOCKED`؛ نجاح التوليد يعني سلامة إعداد المراجعة فقط. المجلد الأب يجب أن يكون موجودًا، ولا يعاد استخدام مجلد حزمة موجود.

## بوابة العمال التي كشفتها مراجعة العقود

بروفة Linux الحالية استخدمت `NODE_ENV=test` وعمالًا معطلين. أما ProductionReadinessValidator فيعامل `NODE_ENV=staging` مثل production في بوابات الجاهزية، ويضيف BLOCKER عند تعطيل `CERTIFICATE_COMPLETION_WORKER_ENABLED` أو `BACKGROUND_WORKER_ENABLED`. كما يبقى مخطط AppConfig ومزودوه وأسراره الإلزاميون مطلوبين حتى مع تعطيل ميزة؛ لا نحذف هذه المفاتيح لمجرد تجهيز القالب.

لذلك تحفظ الخطة العمال معطلين وحالة التشغيل محجوبة. قبل الإقلاع الفعلي: يُستكمل دليل المسارات المطلوبة عبر use cases والمزود الصناعي الفعلي، والتكرار والتعطل وlease وحفظ الإيصالات، ثم تُراجع تهيئة العمال في مرشح جديد. لا يتغير validator ولا تُفعّل أعلام العمال لأجل إزالة الخطأ. لا يعاد استخدام أسرار المختبر أو `NODE_ENV=test` لتجاوز بوابة staging.

## ترتيب التجهيز الفعلي المتبقي

| التبعية | المطلوب قبل التنفيذ |
|---|---|
| الحساب والميزانية وإقامة البيانات | حساب وبيئة اختبار مفوضان، ميزانية ومناطق معتمدة؛ [AWS اختيار تصميم فقط](R10_AWS_RECOVERY_REVIEW_TARGET_2026-10-20.md) |
| البنية المعزولة | PostgreSQL16 خاص ودور تطبيق محدود، Redis معزول، حيز أصول خاص صناعي منفصل، وأسرار منفصلة عن الإنتاج |
| HTTPS والإصدار | TLS/ingress موثقان، proxy hops الفعلية، cookies/CORS، نفس SHA في API/Web/Admin والعمال، وفحص جاهزية حديث |
| العمال والمزودون | إغلاق متطلبات المسارات المفعلة واستخدام sandbox/stub دون دفع حقيقي أو رسائل طلاب؛ لا إعادة كل فحوص النطاقات الناجحة غير المتأثرة |
| النسخ والاستعادة | الضوابط الفعلية لدى المزود وتجربة الاستعادة وتوقيعاتها وفق العقود؛ نجاح المختبر لا يثبتها |
| التحكم والثقة | تنفيذ/توفير خادم deployment control plane المعتمد وصلاحياته، ومفاتيح الثقة والاعتمادات المطلوبة؛ الموجود حاليًا عميل reconciliation فقط |

بعد استيفاء هذه التبعيات: استرجاع artifact `manaratak-release-artifacts-aaf932e17c10e71d37d7f69a50dfe1c20e7c4b1b` من التشغيل المحدد للمراجعة، والتحقق مجددًا من manifest وكل tar/SBOM والطبقة الأصلية. عند اختيار مرشح أحدث يستبدل المصدر **بأدلته الجديدة**، دون إعادة تسمية الملفات القديمة أو إعادة بناء الحزم بين validation وstaging. تستخدم أداة `post-deploy-smoke.mjs` الموجودة لفحص endpoints الفعلية بعد تفويض الهدف، ثم رحلة متصفح أساسية على نفس الحزم.

تبقى `promote-environment.mjs` محجوبة بإذن الترقية وGO وتوقيعات البيئة الأصلية. لا تُستدعى حتى بوضع تجريبي ضمن هذه الدفعة. يبقى PR مسودة والمراجعة والدمج والنشر قرارات مستقلة.

## التحقق المنفذ لهذه الدفعة

ثلاثة اختبارات مركزة: استعمال الأدلة الحقيقية وإظهار عوائق العمال؛ رفض production أو عامل غير معتمد أو CI فاشل/مختلف SHA أو تطبيق متغير؛ ورفض تعديل بايتات الدليل أو استبدال مساره. يكتمل التحقق بفحص lint للملفات الجديدة وتوليد الحزمة فعليًا على commit نظيف. لا حاجة لإعادة رحلة CMS أو التراجع أو مجموعات R05–R13 المحلية بسبب أداة مراجعة لا تشغّل التطبيق.
