## إجراء معالجة الأدوار المرتفعة — مقترح، غير منفذ

المطلوب إزالة الوصول للأزواج المحددة فقط، دون مالك القاعدة أو الأدوار المحدودة أو المرجع:

- `br-raspy-shadow-ba33tmh3` / `post28_migrator`.
- `br-raspy-shadow-ba33tmh3` / `post28_app`.
- `br-round-dew-bahzpr4x` / `post28_shadow`.

قبل أي حذف، يجري مسؤول Neon مخول جردًا إداريًا لعضويات الأدوار، والجلسات القائمة، وملكية قواعد البيانات والكائنات، وdefault ACLs والاعتماديات في **كل قاعدة في الفرع**؛ بما فيها `manaratak_test` الموروثة. قوائم API وكون protected=false لا تثبت انعدام الاعتماديات. لا تشغيل اختبار تطبيق بدور المالك لجمع ذلك الدليل.

الأولوية تعطيل الدخول/إبطال بيانات الاعتماد والجلسات للأدوار غير المستخدمة عبر إدارة المزود المخولة، ثم حذف الأدوار الثلاثة بعد إثبات عدم استخدامها أو امتلاكها كائنات مطلوبة. `NOLOGIN` وحده لا ينهي الجلسات القائمة. لا يُعاد تنفيذ محاولات REVOKE/NOLOGIN السابقة الفاشلة من جلسة المالك؛ يلزم مسار إداري يدعم العملية أو تصعيد إلى Neon عند نقص السلطة. لا نعتبر محاولة مرفوضة إبطالًا ناجحًا.

إذا ظهرت ملكية أو grants مطلوبة، توقف المعالجة حتى مراجعة نقل محدد لها؛ **لا DROP OWNED CASCADE ولا نقل ملكية شامل ولا حذف قاعدة أو فرع**. بعد الإجراء تُعاد قراءة provider/catalog والجلسات وتثبت عدم إمكان المصادقة بالأدوار القديمة، وتحفظ النتيجة دون أسرار. هذه الجولة حددت الإجراء ولم تحذف أو تغيّر أي دور.

## إعدادات لا تملك هذه الجلسة تهيئتها

فحص البيئة الحالي: spec revision67 وobservations_current=true، لكن secret bindings/runtime variables/outbound identities فارغة. جميع أسماء الاتصال المفحوصة غير موجودة في بيئة العملية. الأدوات المتاحة تقرأ حالة البيئة ولا توفر عملية كتابة أسرار آمنة؛ لا أستطيع توليد كلمة مرور ثم تمريرها في دردشة أو SQL tool مسجل بدل مخزن الأسرار.

يلزم من مسؤول البيئة/Neon:

1. تهيئة مصادقة كلمات مرور قوية ومستقلة للأدوار المحدودة الثلاثة عبر قناة إدارة خاصة تمنع ظهور القيمة في argv أو السجلات، مع إعادة فحص flags/membership بعد التغيير؛ لا إنشاء بديل عبر API يمنحه neon_superuser تلقائيًا.
2. حقن أسرار الاتصالات المباشرة في **بيئة التنفيذ الحالية**:

   | اسم السر | الهدف والدور |
   |---|---|
   | `GREENFIELD_DATABASE_URL` | DB-G / `post28_g_migrate_limited` |
   | `GREENFIELD_SHADOW_DATABASE_URL` | DB-S / `post28_s_shadow_limited` |
   | `DATABASE_URL` و`DIRECT_URL` | DB-G بنفس الدور المحدود خلال فحص الزوج فقط؛ ليس إعداد app role للتشغيل |
   | `NEON_API_KEY` | قراءة بيانات project/branch/endpoint/database/role اللازمة للتحقق؛ خارج Git والدردشة |

   يحتفظ اتصال التطبيق المحدود منفصلًا، مثل السر الخاص المقترح `POST28_NEON_DB_G_APP_DIRECT_URL`؛ هذا الاسم **ليس متغيرًا يستهلكه المشغّل الحالي**. يلزم مسار فحص قراءة مراجَع له دون إعادة تسمية DB-G إلى DB-T لتجاوز الحارس.

3. تفعيل تصريح TCP عبر إعداد بيئة Codex المدعوم للمضيفين **بالضبط**:
   - `ep-red-king-baoyw96q.c-8.eu-central-1.aws.neon.tech`، منفذ5432.
   - `ep-tiny-recipe-ba15g3br.c-8.eu-central-1.aws.neon.tech`، منفذ5432.

   السياسة الحالية domains=[] وip_ranges=[]؛ HTTPS unrestricted ليس تصريح PostgreSQL. لا تعديل يدوي لملف السياسة أو تعطيل proxy/TLS، ولا أعلام CI للتحايل. أعد فحص الحالة بعد تفعيل إعداد البيئة وتجديد الجلسة إذا تطلبت المنصة ذلك.

4. عقد هدف خاص خارج Git يشير إليه `POST28_TARGET_CONTRACT_FILE`، مربوط بأحدث HEAD نظيف وUUID جديد، وبـREAD_ONLY_PREFLIGHT وG/S والأدوار المحدودة المسجلة. القالب في [دليل القراءة فقط](POST28_NEON_READ_ONLY_PREFLIGHT.md). استخدم Direct مع `schema=public&sslmode=require&sslaccept=strict`، لا pooler، ولا رابط المالك.

## قرار R03 وR04 ونقطة الاستئناف

R03 لا تُغلق: المصادقة والأسرار وTCP وTLS/Prisma وفحوص SQL المستقلة للأدوار، ومعالجة الأدوار القديمة، وبقية خدمات المختبر/ميزانياته، لا تزال غير مثبتة. لا تقرير جاهزية R04 إيجابي ولا تنفيذ ترحيلات أو seed أو suites مدمرة أو إنتاج أو main.

**توقف التنفيذ المعتمد على الإعدادات هنا وفق طلب المستخدم.** نقطة الاستئناف: بعد معالجة الأدوار وتهيئة الأسرار وتصريح المضيفين، تحقق من أحدث HEAD وحالة البيئة، ثم شغّل فحص الزوج بالقراءة فقط من Node22:

```bash
node scripts/database/post28-preflight.mjs --pair --require-empty
```

قارن provider binding وSQL session/TLS/ACL وOID وعدم alias، وافحص دخول التطبيق بصلاحياته المحدودة، ووثّق النتائج الفعلية دون مالك. إذا اجتازت جميع بوابات R03، عندها فقط يُكتب تقرير جاهزية R04 بأوامر التنفيذ ونطاق DB-G/DB-S؛ تبقى الترحيلات منتظرة تفويضها.

**فحص حي إضافي بالقراءة فقط عبر جلسة Neon المخولة** (وليس اتصال Prisma من Codex) على فرعي G/S أظهر في `pg_authid`:

|---|---|---|---|
| `post28_g_migrate_limited` | `true` | `true` | `false` |
| `post28_g_app_limited` | `true` | `true` | `false` |
| `post28_s_shadow_limited` | `true` | `true` | `false` |

هذه النتيجة تحسم أن أدوار SQL محدودة الصلاحيات **تملك خاصية LOGIN، لكنها بلا كلمات مرور**؛ ولهذا يعرض Neon API `authentication_method=no_login`. لا تنشئ بدائل عبر `create_postgres_role` الافتراضي؛ قد تُنشأ صلاحيات مرتفعة. عيّن كلمات مرور قوية للأدوار الموجودة **بواسطة واجهة Neon المعتمدة أو مسار إداري خاص آمن**، واحفظ بياناتها مباشرة في مدير أسرار بيئة Codex. لا تمرر الأسرار عبر أدوات SQL المسجلة أو محادثات الدردشة أو Git، ولا تحاول إنشاء كلمات مرور ضمن تقارير الفحوص.

**تفاصيل اتصال Codex بعد التجهيز:** يحتاج المسار الخاص للقراءة فقط `GREENFIELD_DATABASE_URL` بدور `post28_g_migrate_limited`، و`GREENFIELD_SHADOW_DATABASE_URL` بدور `post28_s_shadow_limited`؛ `DATABASE_URL` و`DIRECT_URL` عندما يتطلبها Prisma لقاعدة G بنفس الدور، و`NEON_API_KEY` بصلاحيات قراءة provider محدودة، و`POST28_TARGET_CONTRACT_FILE` لمسار عقد غير سري خارج checkout. نقاط Direct المضبوطة مسبقًا في registry فقط؛ لا pooler أو wildcard.

**تنبيه الشبكة:** لا تعني إضافة نطاق إلى قائمة HTTP(S) السماح باتصال PostgreSQL TCP/5432. يجب إثبات دعم البيئة الفعلي لتصريح TCP إلى hostَي Direct، وإلا يبقى الاتصال المباشر `BLOCKED` ويُستخدم مختبر تشغيل يدعم TCP مع أسرار معزولة. لا تحايل عبر CI أو تغيير اسم الهدف.

لم يُغيّر هذا التحقيق صلاحيات الأدوار أو كلمات المرور أو أي سجل تطبيق، ولم يُنفذ migration أو seed أو اختبار runtime. نتيجة `R03=BLOCKED_RUNTIME_CONFIGURATION` باقية. التقرير السابق `fb3fb097` يحتفظ ببصمة `a3dbee92` كمصدر مفحوص ولا تُنسب إليه هذه القياسات الجديدة.
