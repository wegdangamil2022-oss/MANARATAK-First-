### سياسة CSRF والجلسة

- أصبحت الاستثناءات مجموعة مسارات كاملة بعد تطبيع case والشرطة النهائية، مع احتساب `baseUrl + path`. لا substring/prefix/suffix matching.
- الاستثناءات الافتراضية تقتصر على login/register/verify-email/resend-verification/forgot-password/reset-password تحت `/auth` أو `/api/v1/auth`. مسار refresh لم يعد مستثنى، وله حارس داخل الراوتر أيضًا، مثل logout.
- وجود كوكي وصول دون كوكي تحديث يرفض التعديل بـ`CSRF_SESSION_REQUIRED`. إضافة Bearer إلى طلب يحمل كوكي لا تعفيه؛ المصادقة القائمة تقرأ الكوكي قبل الترويسة.
- Bearer بلا أي كوكي يبقى خاضعًا لمصادقة المسار، ويجتاز جانب CSRF الافتراضي لأنه لا يحمل اعتمادًا متصفحيا ضمنيًا. إذا ضبط `exemptBearerAuth:false` يطبق الرفض عند غياب session binding.
- فحص Origin في تركيب التطبيق يستخدم قائمة frontend origins نفسها المعتمدة لـCORS، ويسمح بالمصدر نفسه للـAPI. المصدر الأجنبي، أو cross-site metadata دون Origin، يُرفض في التعديل حتى على مسارات الدخول العامة. CORS وحده لا يمنع تنفيذ طلب تعديل.
- GET الخاص بإصدار CSRF يتحقق من refresh token، ومن وجود الجلسة ونشاطها وحالة الحساب، ويربط HMAC بالكوكي الفعلي. لا يقبل CSRF من body/query.

| نوع الطلب | السلوك |
|---|---|
| GET/HEAD/OPTIONS | جانب CSRF يسمح؛ حماية المسار نفسه مستمرة |
| دخول/تسجيل عام، بمساره الكامل | لا يحتاج CSRF قبل تكوين جلسة؛ فحص Origin قائم |
| تعديل بكوكي تحديث | يحتاج توكن صالحًا مرتبطًا بنفس الكوكي |
| تعديل بكوكي وصول فقط | 403، ولا ترويسة تعفيه |
| Bearer مع كوكي | يعامل كطلب كوكي ولا يتجاوز الحماية |
| refresh بكوكي | يحتاج CSRF ثم التحقق/التدوير من خدمة المصادقة |

### عميل الويب والإدارة

العميلان يستعملان `CsrfClientManager` القائم، ويتخلصان من التوكن بعد تدوير كوكي التحديث. الويب كان يغفل هذا المسح؛ أصلحناه. استجابة 403 من محاولة refresh لا تُفسر تلقائيًا على أنها رفض دائم لرمز التحديث؛ يبقى 401 هو الرفض الدائم في مسار refresh، مع استمرار قواعد عدم إعادة أوامر فاشلة بلا نجاح التجديد.

أضيف generation لطلبات bootstrap لمنع استجابة جلسة قديمة من إعادة ملء الكاش بعد rotation/logout. إعادة CSRF مسموحة مرة واحدة ولرمز `CSRF_TOKEN_INVALID` تحديدًا، مع استبدال الترويسة القديمة دون ازدواج اختلاف الأحرف، والحفاظ على body ومفتاح idempotency للأمر نفسه.

### ميزانيات auth وعدم كشف وجود الحساب

حد المعدل العام يبقى قائمًا. أضيفت ميزانيات مستقلة قبل حالات الاستخدام، وتعمل أيضًا للمعرف غير الموجود:

| المسار | لكل حساب/توكن | لكل IP |
|---|---|---|
| register | 5 لكل ساعة | 20 لكل ساعة |
| verify-email | 10 لكل 15 دقيقة | 40 لكل 15 دقيقة |
| resend-verification | 1 لكل دقيقة | 10 لكل دقيقة |
| reset-password | 5 لكل 15 دقيقة | 20 لكل 15 دقيقة |

مفاتيح البريد/التوكن HMAC-SHA256 بمفتاح الخادم وبوسم غرض منفصل؛ البريد يطبّع قبل الاشتقاق، ولا يخزن البريد أو توكن الاستعادة الخام في المفتاح. حدود login القائمة تبقى بأرقامها، مع استخدام الاشتقاق الموثوق نفسه. ترويسة Retry-After موجودة عند 429، وتعطل مخزن المعدل يؤدي إلى 503 قبل العملية.

**تغيير عقد مقصود:** register يعيد `202` مع `{ registrationPending: true, message }` للحساب الجديد والموجود، دون identityId أو تمييز 409. عُدّل نوع العميل ونص نجاح التسجيل ليتوافقا؛ المستهلك الحالي يتابع إلى إرشاد البريد ولا يستعمل identityId. تستعمل حالة الحساب الموجود dummy credential verification عند توفرها، لكن هذا لا يثبت مقاومة قياس الزمن بالكامل أو وصول البريد الفعلي.

### الأسرار وDI

- سياسة رفض مشتركة بين AppConfig وProductionReadiness ترفض القيمة الافتراضية المعروفة لـCSRF وأنماط التطوير والplaceholder، بالإضافة إلى حد الطول. طول السر لا يثبت مقدار العشوائية؛ قيمة الإنتاج يجب أن تأتي من إدارة الأسرار.
- أزيل إنشاء ForgotPassword/ResetPassword ومستودع الذاكرة وPasswordHasher والوصول الخام إلى Prisma من AuthRouter. الراوتر يشترط حالات الاستخدام المحقونة واشتقاق مفتاح المعدل، ولا ينشئ بدائل.
- composition root يرفض مستودعات رموز الذاكرة ومزود البريد captured في production/staging، ويطبق هذا الحد للمصادقة أيضًا عند اختيار production عبر runtime profile. التغيير لا يعيد تعريف productionLike لبقية المالكين.
- حُذفت نقطة `/auth/diagnostic/captured-emails` التي كانت تعتمد على صنف infrastructure داخل طبقة العرض وتكشف رموز التطوير. لا يوجد مستهلك حالي لها في المستودع.

1. الحارس الحالي ومسارات AuthRouter واختبارات clients القائمة.

4. منع prefix/substring، وBearer مع كوكي، وaccess-only، وتوكن جلسة أخرى، وOrigin أجنبي، وinactive session، وخيار bearer=false.
5. حدود المسارات الأربعة قبل الأعمال، وغياب البريد/التوكن الخام في مفاتيحها، وتعطل مخزن الحدود، ورد تسجيل متطابق.
6. استجابة bootstrap قديمة بعد clear/rotation، وترويسة CSRF lowercase قديمة عند retry.
7. اختبارات composition root الفعلية في production وstaging وproduction profile مع prisma=null: لا ذاكرة لرموز الاستعادة/التحقق، ولا captured email، ولا مفتاح معدل مبني على default التطوير.

- نشر API وعملاء web/admin المتوافقين معًا، أو نشر العميل المحدث أولًا مع كاش مضبوط؛ عدم إزالة حماية refresh كحل لتوافق عميل قديم.
