# مراجعة الخطة مع المصدر بعد الدمج في main

الأساس بعد fetch: `38c84e60f7be5cb9e0f4db8ceb588a3637c78c20`؛ main وفرع العمل متطابقان ونظيفان عند بدء المراجعة. توجيه المستخدم السابق أجاز نقل العمل إلى main، والطلب الحالي مراجعة النواقص وإصلاح المثبت منها. هذه متابعة للخطة نفسها؛ لا تغيير تاريخ الترحيلات أو بيانات تشغيلية.

## نطاق المقارنة

قورنت صفوف B01–B14، ومنها B10a–d، ومراجع التقارير والمواصفات وسجل البنود الـ54 مع المصدر الحالي. روجعت خصوصًا حدود الأوامر التي أضيفت في B13، هوية المالك والموافقة وreceipts، قراءة موافقة الخريجين في B12، وبيانات الفحوص التي لم تُعد. أدلة الحزم السابقة لا تنسب إلى هذه الجولة ولا تعاد تلقائيًا. هذا تدقيق متابعة محدود للخطة؛ لا شهادة شاملة لكل أخطاء المستودع أو كل متطلبات المراحل التاريخية.

## نواقص مثبتة أُصلحت

| النقص | المثال والأثر | الإصلاح |
| --- | --- | --- |
| هوية القيد عند ربط موافقة العكس | إنشاء الموافقة يثبت `ledger.id`، لكن التنفيذ بمرجع `publicId` كان يبني target/hash مختلفًا فيرفض موافقة صحيحة | قراءة القيد من المالك ثم استعمال ID نفسه في target/hash/receipt والعكس؛ قراءة وجود عكس سابق لا تمنع وصول retry إلى receipt |
| مصدر موافقة مكوّن من whitespace | `String.trim()` يرفض TAB/NBSP/BOM، لكن `btrim(source)` الافتراضي في PostgreSQL يزيل space العادي فقط؛ اختلاف غير مقصود في شروط الدليل للصفوف القديمة | تمرير مجموعة محارف String.trim الكاملة كمعامل SQL إلى `btrim`؛ لا افتراض أن الصفوف القديمة تحمل موافقة ولا قائمة مصادر مخمنة |
| دفاع maker في التطبيق | نقل فحص أهلية checker كله إلى المالك أزال الرفض المبكر للمُنشئ في التطبيق، وأبطل اختبارًا قائمًا لذلك الحد؛ المالك ظل يرفضه | رفض maker دائمًا في التطبيق أيضًا، مع إبقاء تاريخ قرارات checker بعد lookup receipt داخل معاملة المالك كي لا ينكسر replay |
| بدائل اختبارات قديمة لا تتبع عقد receipt | مصنعا DB في اختبارات المالية لا يوفران FinanceCommandRecord؛ اختبارات مبلغ hold صارت تفتقد الإصدار الإلزامي فتختبر الإصدار بدل المبلغ | إضافة بديل receipt يحفظ الصفوف ويرفض تكرار المفتاح إلى المصنعين، وتمرير expectedVersion الصحيح لاختبار المبلغ؛ تحديث assertion صيغة trim في اختبار الدليل |

لم يُضف مالك أو schema أو ترحيل أو سياسة موافقة أو مدة احتفاظ. لم تتغير شروط نشر المسودات أو صلاحيات الموظفين أو موافقة صاحب المحفظة. توجد سياسة مزود مالي فعلية تعتمد `FINANCE_RUNTIME_APPROVED` في DI؛ لم تُغير أو تُفعّل، ولا تُفسر كدليل جاهزية فعلية.

## الفحوص الفعلية

- تشغيل واحد جديد ومحدد: ملفان و**10/10 PASS** في 6.99 ثانية. شمل alias/internal ID للعكس، هدفًا مفقودًا أو مختلفًا، فصل maker، تفويض retry للمالك، محارف SQL المربوطة للصفحة والعدد، والمالك المالي الحقيقي مع receipt/decision/outbox مرة واحدة ورفض تغيير النية. بدائل ذاكرة، بلا DB.
- فحص أنواع واحد دون emit: PASS للمصدر الحالي، ويشمل تصحيحي HTTP السابقين من ناحية الأنواع فقط؛ ليس إعادة فحص سلوكهما.
- ESLint للملفات المحددة: صفر أخطاء و55 تحذيرًا؛ `git diff --check` ناجح. تغيير مدخل اختبار المبلغ الأخير فقط تلا lint، وليس مصدر التطبيق.
- [الأوامر والمخرجات وبصمات الملفات ونطاق المقارنة](evidence/postclosure-review-2026-10-15/summary.json).
- لم تعد مجموعة B13 القديمة أو فحص V8 للائتمان أو suite section20 أو الفواحص السبعة التاريخية. التحديثات في بدائل الاختبار لا تعني أن مجموعاتها أُعيدت أو نجحت. لا build أو اختبار شامل/ثقيل أو DB أو متصفح أو مزود أو worker أو أثر حقيقي.
