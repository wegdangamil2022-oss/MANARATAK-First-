# Section 25 rollout and recovery — runtime deferred

No Prisma model or SQL migration is added by section 25. Do not apply previous sections' migrations from a health endpoint. The database-schema indicator proves only that applied migration history has no incomplete entries; schema drift and required migration parity still require the deployment owner's separate artifact.

Before runtime acceptance after section 28:

1. Use the supported Node runtime and reviewed source artifact. Provision `HEALTH_DEPLOYMENT_REVISION` identically for API and workers of the same release. Their environment and API origin must also match. Missing revision/Redis observation means unavailable cluster evidence, not healthy workers. Observations expire after one hour; their accepted age is separately bounded by the owner polling interval. A stopped worker's last success may remain visible only within this freshness budget. Existing Redis IAM/isolation and TLS policy must be preserved.
2. Provider owners must approve and implement authenticated `GET /v1/capabilities/readiness` using the existing SignedProviderHttpClient authentication. Expected JSON: `{protocolVersion:1, checkedAt:ISO, capabilities:{CAPABILITY:{ready:true,authorized:true}}}`. Capability names: `asset-storage`, `malware-scanner`, `asset-sanitizer`, `import-raw-archive`, `finance-payment`, `notification-delivery`. This must verify the current credential's actual scope and dependency availability without uploads, malware jobs, messages, ledger writes or payment authorization. It must not disclose credentials/PII. Missing, stale, unauthorized or unsupported contract fails closed. Notification delivery capability must include its durable reconciliation contract; payment capability does not replace Finance runtime approval. The client uses a two-second bound, parent abort and existing bounded response streaming.
3. Review Finance owner runtime approval and configuration. This deployment already exposes paid services, so production payment health is required. Do not mark that vertical optional merely to get a green gate. Product-disabled deployment policies require owner route/config changes and approval, not an invented monitoring override.
4. Complete read-only schema/required migration parity and IAM/session-store acceptance. Public monitoring v2 no longer returns details/indicators. Admin consumers use the guarded overview; external probe consumers must migrate to the versioned four-field allowlist.
5. In disposable staging, capture an environment/build/commit/time-bound signed health artifact. Verify public/admin permission and redaction boundaries, required-degraded/timeout behavior, public web 2xx/redirect/401/404/429 cases, provider authorization failure, actual telemetry export and age, DB/Redis timeouts, cross-pod worker success/staleness, queue lag, and AR/EN keyboard/browser behavior. Record owner sign-off and rollback evidence. Production approval remains separate even when diagnostic gates pass.

Health reads do not publish Redis heartbeats or invoke provider mutations. Workers publish observations only on their actual paths; failure to persist evidence cannot fabricate health. Process-local history stores only component IDs/status/time, retains bounded samples and is erased on process restart. It is explicitly partial and must not replace the current release gate or central telemetry history.

Recovery: roll back the source artifact as one unit if necessary, including public/admin protocol consumers. Redis observations are revision-scoped and expire naturally; no database purge/reset or provider credential rotation is needed for this code change. Preserve previous sections' data, migration and provider recovery procedures.
