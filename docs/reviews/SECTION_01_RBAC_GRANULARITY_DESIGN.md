# 01/P1-04 — مهمة تصميم تفصيل الصلاحيات

حالة الوثيقة: تصميم مرحلي للمصدر، وليست ترحيلًا لأدوار أو قبولًا تشغيليًا. القاموس المركزي هو `packages/shared/src/authorization/adminPermissionCatalog.ts`؛ صلاحيات المنفذ تُقيّم خادميًا قبل التفويض. تظل السياسة قابلة للإعداد الإداري، ولا تُستنتج تعارضات من أسماء الأدوار.

| المجال | فصل الإجراءات المقترح / الموجود | ضابط التنفيذ المرحلي |
|---|---|---|
| Identity/Auth | إدارة الهوية منفصلة عن إدارة بيانات الاعتماد؛ MFA reset بموافقة مستقلة | لا تجعل إدارة الأدوار شرطًا لصفحة الموظفين |
| Authorization | إدارة الأدوار والسياسات والتعيينات والوصول الطارئ | الاحتفاظ بمنع التصعيد والموافقة وCAS؛ أدوار الموارد/JIT العادي مرحلة لاحقة |
| Audit | عرض السجل؛ قراءة/إدارة القضايا؛ إدارة التنبيهات؛ إدارة الاحتفاظ | القضايا لا تمنح صلاحية مالك الهدف؛ إنشاء التنبيه يتطلب صلاحية نية الإشعار |
| Assets | read/use عبر reuse؛ إدارة دورة الحياة منفصلة | استخدام الملف لا يمنح archive/delete/purge؛ إعادة تحقق عند حفظ المالك |
| Finance | كتابة العمليات واعتمادها وإدارتها بحسب القدرات الموجودة | جرد كل route + actor/context قبل فك بوابة workspace الواسعة؛ لا تحويل جماعي في هذه الجولة |
| Publications: Universities/CMS/Courses | قراءة، تأليف، مراجعة، نشر/إلغاء، أرشفة، استيراد | لكل مالك patch مستقل: ربط guard، واجهة، تحقق تفويض، ثم توافق موثق مؤقتًا |
| Certificates/Notifications/Services | المحافظة على القدرات المنفصلة الموجودة | عدم جمع قدرات PII أو delivery أو approval ضمن manage عام جديد |
| بقية المجالات | الجرد من owner routes ثم تحديد view/create/edit/review/publish/archive/import الفعلية | لا إنشاء permissions شكلية قبل تحديد command owner ومعايير الوصول |

لكل patch لاحق: احصر endpoints والأوامر الفعلية، اربط كل فعل بقدرة مركزية، أبقَ CSRF/idempotency/audit والقيود السياقية، أضف حالات رفض للصلاحية الأعلى والقراءة بلا كتابة، وثّق توافق الأدوار القديمة وخطة إنهائه. أي ترحيل بيانات أدوار أو تطبيق schema يحتاج تجهيزًا منفصلًا؛ لم يحدث هنا.
