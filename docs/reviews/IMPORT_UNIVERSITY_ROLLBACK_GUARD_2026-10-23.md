# حماية تعويض استيراد الجامعة من الانحراف

اختبار RED أثبت أن التعويض القديم يمر في أربع حالات غير آمنة: تعديل اسم الجامعة، نشرها، تغيير سجل المصدر، أو إضافة ترجمة جديدة. الخطر محو تعديل لاحق أو حذف علاقة عبر Cascade عند حذف جذر CREATE.

الحارس الجديد يقفل جميع الجامعات المرتبطة مرتبة بمعرّفاتها قبل أي تعديل، ويرفض الجامعة المفقودة أو ذات الحالة المحصنة. لجذر أنشأته الدفعة يقارن أعداد العلاقات بالتغييرات التابعة التي أنشأتها الدفعة نفسها، ويشمل ذلك عدد إيصالات importChanges؛ أي علاقة إضافية تحجب التعويض. ثم يقفل كل سجل متأثر من خريطة جداول ثابتة ويقارن كامل حقوله بعد توحيد JSON مع afterState المحفوظ. أي نقص أو انحراف يمنع الدفعة قبل حذف أول مصدر أو إعادة أول قيمة.

لا قيمة خارجية تدخل اسم جدول SQL: الأسماء محصورة بخريطة داخلية وentityId parameterized. أقفال FOR UPDATE للوالد تحميه من تعديل موازٍ وتحجب إدخال طفل جديد بمفتاح أجنبي أثناء التعويض. حارس ADMISSION_REQUIREMENT السابق باقٍ. لا ترحيل أو استثناء صلاحيات أو تعديل تاريخ.

نجحت الحالات الأربع بعد الإصلاح، وأُعيدت حالة التعويض السليم المتأثرة فقط فنجحت معها (5/5؛ بقية 14 لم تُعد). نجح بناء infrastructure وlint للملفين. الإيصالات القديمة التي لا تحتوي afterState أو لم تعد تطابق السجل تفشل مغلقًا وتحتاج مراجعة recovery، ولا تُعاد كتابة الأدلة لتجاوزها. الإثبات موجه أولًا لدفعة Stage 1؛ الترتيبات المعقدة لمراحل الإثراء قد تُحجب للمراجعة بدل حذف آثار متغيرة.
