**نتيجة الإغلاق: BLOCKED؛ R06 PARTIAL وليست PASS/CLOSED.** بدأ الاستئناف من HEAD المحلي والبعيد `7e85306653ddd035f8cb94a118a942792d473150` على فرع العمل نفسه. نُفذت76 حالة PostgreSQL جديدة مختلفة ناجحة؛ التراكمي **243=167+76**، دون جمع إعادة الحالات. هذه نتيجة تشغيل ومراجعة قبول محددة، وليست إغلاقًا بالاسم. طلب المالك إغلاق المرحلة لا يتضمن اعتماد DEC-01…07 ولا يوسع الاستثناء المحلي المحدود في `post28-stage-disposition.json` إلى قبول الترقية أو الإنتاج.

## ما أُصلح فعليًا

1. **إعادة نتائج خاصة بعد سحب الصلاحية:** أثبت HTTP الحقيقي إمكانية إرجاع نتيجة الجامعة أو attestation أو إصدار الفاتورة القديمة بعد سحب الصلاحية. صار حارس الجامعة ومراجعة الوثائق يسبق replay العام، وبقيت المالية عند سجل أوامر المالك الذي يتحقق من صلاحية الإجراء قبل replay؛ أثبت الاختبار سحب صلاحية invoice وحدها مع بقاء صلاحية finance العامة. بقي replay المشروع دون owner/audit/outbox إضافية. استخدمت الاختبارات callback المثبتة في `app.ts` باستخراج TypeScript AST، والـrouters وJWT والجلسات وRBAC وCSRF والمخازن الفعلية؛ لم يُشغّل bootstrap كامل API بخدماته الخارجية أو MFA إنتاجي.
2. **دليل الاختبار في المنحة:** status=PUBLISHED وحده لم يكن كافيًا؛ ظلت متطلبات الاختبار ظاهرة بعد إخفائه أو سحب نسخته الحالية. أصبحت قراءة المنحة عبر HTTP تستلزم ظهور الاختبار ونسخته المنشورة التابعة له، ويتطابق فلتر الاختبار والعدد مع هذه الشروط، دون الاعتماد على FK وحده.
3. **لغة الدورة:** كان المرجع المتقاعد مع isActive=true يمر في المراجعة، وكانت بطاقات/قوائم دورات ذات مرجع متقاعد أو source label غير محسوم تظهر. أصبحت المراجعة تتطلب ACTIVE مع العلم، وتتشارك البطاقة والقائمة وقراءات العلاقات شرط اللغة المعياري قبل اختيار الصفحة والعدد. يستخدم المسار العام استعلام `findPublishedBySlug` صريحًا، دون fallback إلى استعلام المالك الخام. ويمنع دليل المصدر غير الساري اجتياز حارس النشر. لا اعتماد لسياسة مجانية جديدة أو لـDEC-07.
4. **refund دون مزود:** كان الحجز واستهلاك الموافقة يحدثان قبل اكتشاف أن مزود الدفع غير مهيأ. صار التحقق من التهيئة قبل هذين الأثرين؛ أثبت الاختبار عدم تغير الموافقة والـrefund والقيد والتدقيق والـoutbox. لم تُستدعَ بوابة خارجية ولم نختبر refund ناجحًا لدى مزود حقيقي.

تمثل هذه الأسباب تسع حالات فشل منتج فعلية في الجولات الأولى، ثم نجاح الحالات التسع بعد الإصلاح. لا تُحسب أخطاء تجهيز الاختبار كعيوب منتج.

## حدود ما أثبته التشغيل

- **attestation:** خدمات المراجعة والـrouter ومرجع المنحة وسياسة الأصول ومستودعاتها حقيقية. أثبت VERIFIED/REJECTED، ربط checksum/الطالب/النسخة/الدورة، stale revision، موافقة مسحوبة، مالك/دورة مسحوبة، أصل أجنبي أو دليل bytes متناقض، منافسة مراجعين وrollback PostgreSQL. سجل الأصل CLEAN وأدلته السابقة synthetic معلنة؛لم تُرفع/تفحص bytes لدى مزود حقيقي. لم يُهيأ storage gateway فعلي في المختبر؛رفض use case التسليم الحقيقي الطلب بـ`ASSET_SECURE_DELIVERY_NOT_CONFIGURED`. هذا لا يفحص إعداد مخزن خارج المختبر،ولا يثبت رابطًا مُسلَّمًا أو إبطال رابط قديم.
- **التعلم والشهادات:** إنشاء enrollment والـcompletion ومعاملة audit/outbox حقيقية؛التقدم100% تجهيز synthetic معلوم، وليس تقييم تعلم كاملًا. ثُبت retry والتزامن والتراجع، ورفض enrollment/progress/completion لدورة خارجية، ورفض إصدار شهادة MANARATAK لها. يقر العامل الحقيقي event غير مؤهل دون إصدار، ويترك الإشارة المحلية المؤهلة التي لا تملك template معتمدًا في فشل قابل لإعادة المحاولة. لم تُصنع authority أو template أو شهادة أو inbox وهمية لإعلان نجاح الإصدار.
- **الاستيراد:** هوية provider/native-key/language تتحد عبر اتصالين، وتبقى منفصلة لاختلاف المزود أو اللغة. أصل النطاق/history ورفض stale link-check وتغيير الهوية خارج الاستيراد مضبوط. دليل redirect المدخل synthetic لا يثبت فحص شبكة خارجيًا أو provenance لدورة مستوردة حقيقية. لا إثبات كامل لـimport→owner approval أو crash/ack recovery.
- **المالية:** credit note والتقسيط وحجز المحفظة/فكه/التقاطه ومعاملات القيد متحققة فعليًا، مع replay/conflict/version/CAS وفشل SQLSTATE22012 وتراجع القيود والتدقيق والـoutbox والـreceipts. رصيد افتتاح المحفظة قيد تاريخي synthetic متوازن معلن،وسجل الدفع CAPTURED المستخدم لتجهيز refund تاريخي synthetic أيضًا؛لا يثبت تحصيلًا لدى مزود. أثبت الالتقاط المحلي تسوية ledger واحدة وسداد الفاتورة؛هذا ليس bank settlement أو دفعًا خارجيًا. غياب المزود يمنع request/settlement، وتُظهر reconciliation عدم التوفر دون تصنيع CAPTURED/SETTLED.

## لماذا لم تصبح R06 CLOSED

الخطة تنص صراحةً في [قبول R06](POST28_ISOLATED_VALIDATION_EXECUTION_PLAN_v1.3_2026-10-16.md#L219): «لا تغلق هذه البوابة قبل تنفيذ حالات DB/owner الإلزامية… خاصة الاقتران المركب degree+major+program، والتزامن لمنع duplicate test requirement، والإبطال الذري لإسقاطات CourseMajorProjection». النجاح المحلي لا يعوض هذه الحالات أو اعتماد المالك.

1. **R05 prerequisite:** orphan ما زال بعائقه؛مراجعة الإصلاح لا تثبت نجاح upgrade109→110 أو العميل القديم أو استئناف الترقية والانقطاعات/lock budgets. الاستثناء يسمح بفحوص R06 مستقلة فقط.
2. **قرارات المالك:** DEC-01 اقتران المنحة، DEC-02 بلادها، DEC-03 مجانية الدورات، DEC-04 مستوى عرض دورات التخصص، DEC-05 إبطال الإسقاطات، DEC-06 منع التكرار مع Nullable، DEC-07 السوق/لغة التدريس؛كلها بلا ownerApproval معتمد في السجل. أكد المالك خلال هذا الاستكمال أنه لا يملك مراجع قرارات معتمدة؛حُفظ رده في closure-assessment. طلب الإغلاق ليس بديلًا عن مضمون هذه العقود.
3. **بقية القبول التشغيلي:** النشر الكامل وتاريخه عبر المالك والواجهات، learning-path→credential، import→owner/crash recovery، الإبطال الفعلي لرابط تخزين مُسلَّم، وكل مصفوفة lifecycle متعددة الصفحات لم تثبت كاملة. عدم تنفيذها ليس عائق خدمات تلقائيًا؛تفصل closure-assessment بينها وبين غياب authority/storage أو منع المزود الخارجي. صفر صفوف قبول كاملة مثبتة، ولا ادعاء قبول26 حالة من عدّ243 حالة أصغر.

**نقطة الاستئناف:** مراجعة closure-assessment والمصفوفة الجديدة، واستكمال شروط القبول غير المثبتة؛تُمنع فقط الإجراءات التابعة لقرارات DEC إلى أن يقدم المالك عقودها المعتمدة. لا تعاد243 حالة إلا بقدر تأثرها بتغيير جديد. لا نشر أو دمج main أو تغيير سياسات تجارية ضمن هذا التسليم.
