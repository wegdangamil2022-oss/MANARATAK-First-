## ما أصبح يعمل فعليًا

- استُرجعت حزم API/Web/Admin ذات المصدر المحدد من مخزن Actions وفُحصت بصماتها. شُغلت نسختان من صورة API نفسها على Linux x64 وNode 22.16.0، مع PostgreSQL 16 جديد وRedis مستقل وشبكة Docker داخلية وبيانات صناعية فقط.
- أكمل Chromium عبر HTTPS الدخول من الواجهة، والتحقق من الجلسة والتجديد بين النسختين والخروج وإلغاء الجلسة عبرهما. Cookies آمنة وHttpOnly وStrict؛ رفض التجديد دون CSRF. فُحص توافق SHA للوحدات الثلاث. [الدليل الخام للتشغيل والتنظيف](../reviews/evidence/post28/cbb99ac63bb4497df9c07cf3e16611d27bcd3396/r08-combined-closure/evidence-index.json).
- ثماني محاولات دخول غير صحيحة موزعة بين النسختين أعادت 401؛ التاسعة أعادت 429، مثبتة مشاركة العداد. قطع Redis أعاد 500 دون إنشاء جلسة أو التحول إلى عداد محلي. بقيت العمليتان قابلتين للإيقاف السليم وخرجتا بالرمز صفر، وأزيلت مواردهما والقاعدة وRedis والشبكة المملوكة.
- عند فقد رد استرداد مالي صناعي، بقيت النتيجة غير مؤكدة، ولم يُرسل استرداد آخر أو تُستهلك الموافقة مرة ثانية. بعد انتظار موعد المصالحة الطبيعي، سُجل استرداد واحد متوازن وأُعيد فتح المستحق الصحيح. وفي مهلة تفويض فعلية لم تصبح الفاتورة مدفوعة ولم يتكرر الإرسال. [الحالتان الجديدتان فقط ونتائج PostgreSQL](../reviews/evidence/post28/cbb99ac63bb4497df9c07cf3e16611d27bcd3396/r08-provider-closure/evidence-index.json).
- أثبت Redis الفعلي نشر فشل العامل وتوقفه، ورفض اعتبارهما صحة حديثة، وحدّ TTL الفعلي بساعة، مع عزل namespace/revision وACL ورفض replay للإشعار الموقع. [إيصال Redis](../reviews/evidence/post28/cbb99ac63bb4497df9c07cf3e16611d27bcd3396/r08-redis-closure/evidence-index.json).

أدلة سباق التجديد وOutbox والانهيار بعد commit والتحصيل المفقود السابقة محفوظة بمصادرها في [تقرير الاستعادة السابق](POST28_R08_FAULT_RECOVERY_2026-10-20.md). لا تُنسب إلى المصدر الجديد، ولم تُعد اختبارات قواعدها الناجحة في هذه الدفعة.

## الإصلاحات المهمة

1. كان اختيار محدد المعدل يتجاهل Redis المصرح به خارج production/staging ويستخدم عدادًا لكل عملية؛ أصبح الإعداد الصريح يستخدم المخزن المشترك ولا يعود إلى المحلي عند فشله.
2. كانت نتائج العامل التي تحتوي failed/exhausted/leaseLost تُسجل دورات ناجحة؛ أصبحت فشلًا ظاهرًا للـregistry والمقاييس، وتوقف المطالبات اللاحقة في تلك الدورة.
3. كان سجل صحة Redis يحتفظ بالنجاح عند الفشل أو التوقف، ويسقط تحديثًا جديدًا أثناء كتابة سابقة. أصبحت الكتابات مرتبة لكل عامل، وتُنشر حالات الفشل والتوقف، وتستخدم صيغة TTL الصحيحة لعميل Redis المثبت.
4. كشف قطع Redis في الصورة المبنية رفض Promise غير معالج في وسيط تحديد المعدل، وانهيار API. أصبح الخطأ يصل إلى معالج Express مع رفض الطلب. [التشغيل الفاشل المحفوظ قبل الإصلاح](../reviews/evidence/post28/490aa6d997be8b18b450b3958eabe823d2288ef4/r08-combined-closure/evidence-index.json) لا يُحسب نجاحًا.
5. أُزيل عنوان Redis الوهمي من مهمتي فحص المصدر اللتين لا تنشئان Redis. المختبرات الفعلية تنشئ عنوانها الخاص. عُدّلت بوابة أمر المتصفح لقبول وضع R08 المحدد فقط، مع رفض الوسائط الإضافية واستمرار تبعيات الأمان.

## الفحوص وحدودها

أضيفت تسع حالات وحدة مستهدفة: اختيار Redis اثنتان، إخفاقات العامل ثلاث، نشر الصحة ثلاث، ومسار خطأ وسيط HTTP واحدة؛ ثبت الفشل قبل الإصلاح ثم النجاح بعده. أعيدت الحالات الثلاث المتأثرة فقط بعد تغيير الغلاف المركزي، وفُحص عقد CI المعدّل وحده. نجح فحص أنواع API بعد تصحيح حفظ النوع العام. لا بناء كامل محلي متكرر ولا إعادة يدوية للمجموعات القديمة. CI ينفذ بواباته الإلزامية المعتادة عند تغيير المصدر؛ لم تُحذف أو تُضعف assertions أو guards.

تعطل مختبر Windows الجديد قبل بدء حالتي المالية، فلم تُعد محاولات متشابهة؛ نُقل التنفيذ إلى Linux. [إيصال التعطل والفحص اللاحق](../reviews/evidence/post28/1f467c357e13ed376a708a4741c6e9323252027b/r08-native-interrupted/evidence-index.json) يثبت غياب العملية وإغلاق منفذها، ولا يدعي إيقافًا سليمًا أو نجاح الحالات هناك.

المتصفح بلا page errors. حُجبت صور Unsplash الخارجية، وظهرت رسائل console المتوقعة للطلبات السلبية 401/403/429/500؛ لا يدعي الدليل خلو console من هذه الرسائل. عمال الخلفية غير مفعّلين في مختبر جلستي API؛ إثباتاتهم منفصلة، ولم يُفعّل عامل canonical مؤجل.

## مراجعة CodeQL المحددة

التنبيه 160 في `scripts/release/lib/R08CombinedRuntime.mjs:15` يصنف SHA-256 بوصفه تخزينًا ضعيفًا لكلمة مرور. المدخل فعليًا `randomBytes(32)`، سر آلة عشوائي 256 بت جديد لكل Redis صناعي. الحقل `#hash` في Redis ACL يتطلب SHA-256؛ استبداله بـscrypt يكسر المصادقة. هذا نفس سبب مراجعة التنبيه 159 في مختبر Redis السابق، وفق [مراجعة R07 ودليل Redis الرسمي](POST28_R07_CODEQL_REVIEW_2026-10-19.md). يُصنف هذا التنبيه المحدد false positive مع إيصال GitHub؛ لا استثناء للاستعلام ولا إسكات جماعي لتنبيهات المستودع السابقة، ولا ادعاء بخلو المشروع من كل الثغرات.
