# R12 — بدء التراجع المتوافق وحفظ الالتزامات

**أُصلحت بوابة دليل التراجع واكتملت مراجعة مصدر المرشح السابق؛ البروفة الفعلية لم تُنفذ.** القبول الرسمي لـR12 مفتوح، واستثناءات R11 وحالات المراحل السابقة محفوظة.

## إصلاح بوابة القبول

كانت acceptanceDetails تقبل سجل rollback دون previousApiCompatible أو هوية المرشح السابق وبصمات وحداته أو ميزانية canary، وتقبل incidentOwner غير نصي. أصبحت تشترط توافق API والعامل السابقين، وpreviousSourceSha صالحًا مختلفًا عن المرشح الحالي، وبصمتَي API والعامل، ومسؤول حادث نصيًا غير فارغ، وcanaryBudget بصاحب اعتماد نصي وعدد طلبات وتزامن ومدة وحد أخطاء رقميين مضبوطين. تُرفض arrays بدل الهوية/البصمة، واللانهاية وNaN والتزامن أو عدد الأخطاء فوق عدد الطلبات. يبقى التحقق من التوقيعات والسلطات لدى بواباته القائمة؛ لا ينشئ النص وحده اعتماد إنتاج.

فشل الاختبار الجديد قبل التصحيح لأن السجل الناقص كان مقبولًا. نجحت الحالتان المباشرتان بعده: رفض النواقص/القيم غير الصالحة، وقبول عقد تراجع مضبوط دون تمرير بوابات إصدار أخرى. أعيد الملف المحدد مرة بعد إضافة رفض التحويل النصي الضمني للمصفوفات؛ لم تُعد مجموعات المراحل السابقة أو build عام.

## اختيار النسخة السابقة

المرشح الحالي المثبت 4b8e22f4cad6c5cdca384cf3e273c6d5cf97d61b، والسابق c8afe5f253d132f671ecd035a0330de7794b6ee8. تحقق فحص manifest والحزم الثلاث السابقة وبصماتها فعليًا من النسخة المحلية، وتحقق مسار النسب في Git. لا فرق بين مصادر apps/api وpackages وvendor والـlock بين المرشحين، وبصمتا schema/lock متطابقتان. العامل polling مضمن في حزمة API نفسها؛ لا ادعاء بوجود حزمة عامل مستقلة. هذا يجعل السابق مرشحًا للفحص، **ولا يثبت توافقه التشغيلي أو رجوع تنفيذ API مختلف**؛ المصدر التنفيذي للـAPI لم يتغير أصلًا بين الإصدارين.

Admin القديم مستبعد لأنه يسبق إصلاح سباق تهيئة الدخول. لا رجوع تلقائي للوحدات الثلاث، ولا إعادة وسم حزمة قديمة بمصدر جديد. المخطط المختار توقف/بدء مضبوط للـAPI دون نسختين متزامنتين، مع بقاء Web/Admin الحاليين. [مراجعة المصدر والأدلة](../reviews/evidence/post28/601cb572d7ca4663c4d18f7fbf95342c2845bbd3/r12-source-review/evidence-index.json). الأداة inspect-post28-rollback-source.mjs للقراءة فقط؛ تكتب دليلها الجديد خارج المستودع ولا تتصل بقاعدة.

## نطاق التجربة المحلية المجهز

[الإعداد](../../config/testing/r12-local-rollback-preparation.json): قاعدة PostgreSQL16 جديدة صناعية، 24 طلبًا كحد أقصى، تزامن واحد، نافذة canary 60 ثانية وصفر أخطاء غير متوقعة؛ انتظار readiness حتى15 ثانية وdrain حتى20 ثانية. اختار مدير المشروع المفوض هذه الحدود للتشخيص المحلي فقط، ولا يوجد اعتماد canary إنتاجي أو اسم/توقيع مستقل مختلق.

المطلوب في البروفة: تثبيت الحزمتين قبل أي تشغيل؛ fingerprint للـschema؛ حفظ ledger والمعاملات والفواتير والأرصدة/holds والموافقات والـBinding والنشر وAudit/outbox والـreceipts قبل وبعد؛ إيقاف API الجديد قبل السابق؛ إثبات الجلسة/CSRF عبر إعداد صناعي خاص؛ وإعادة receipt حديثة دون أثر جديد. تبقى تجربة العامل السابق وdrain/lease والأحداث الأحدث خطوة مستقلة لم تُنفذ، ولا يجوز تشغيل مزود خارجي أو حذف receipt/DLQ/ledger أو down migration لمحو بيانات.

## العائق ونقطة الاستئناف

تنزيل أرشيف المرشح الحالي 12288633610 تعذر عبر موصل GitHub بخطأ نقل، ثم انتهت مهلة curl عند تنزيل الرابط الموقع. لم يُتحقق digest للأرشيف المحلي ولم يُستخدم أي ملف جزئي. لا قاعدة أُنشئت ولا API/Worker شُغّل ولا بيانات سابقة تغيرت. لم تتكرر المحاولات المتشابهة بعد هذين المسارين.

نقطة الاستئناف: استرجاع الأرشيف المطابق SHA256=bc43f19e0435e834890af468ef340c0832f967beab403d2054116200493ba327 والتحقق من manifest ووحداته، ثم commit معلوم ونظيف وإنشاء المختبر الجديد. تُنفذ بروفة API المحددة، ثم بروفة العامل وفحوص الحفظ والتراجع في routing/config. R12 لا تزال NOT_EXECUTED على مستوى التشغيل، والإنتاج وNeon وmain خارج النطاق.
