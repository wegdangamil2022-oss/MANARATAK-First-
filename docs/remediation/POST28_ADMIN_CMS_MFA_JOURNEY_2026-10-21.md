# رحلة Admin CMS مع MFA — إثبات محلي محفوظ

اكتملت الرحلة العربية من واجهة Admin المبنية: إعداد MFA وتأكيده لثلاثة مستخدمين صناعيين بأدوار منفصلة، ثم تأليف المحتوى وحفظ النسخة وإرساله للمراجعة واعتماده ونشره وسحبه. تأكد ظهور المنشور في المتصفح، وبقاء النسخة المنشورة عند تعديل المسودة، ثم إرجاع 404 بعد السحب مع الرجوع بالتاريخ وإعادة التحميل. رُفض اعتماد المؤلف لمحتواه بـ403، وفُحص منع أزرار الأدوار غير المخولة.

مصدر المشغّل b7748fdd5383103a6936b4310152d49e497c18ae، وحزمتا API/Web من c8afe5f253d132f671ecd035a0330de7794b6ee8، وAdmin من 50e109e3ece76c6b5acb832be9fcd747450821cb. تحقق المشغّل من manifest وruntime ومن عدم تغير مسارات المصدر اللازمة لإعادة استخدام الحزم. هذا تشخيص Windows/Node22/PostgreSQL16 بمصادر متعددة معلومة، وعبر استئناف قاعدة المختبر نفسها؛ لا يمثل مرشح Linux موحد SHA أو قبول الإنجليزية أو حمل الإنتاج.

## الحدود المثبتة

- الاتصال إلى مختبر صناعي جديد فقط؛ دور التطبيق بلا superuser/createdb/createrole/bypassRLS/replication، مع منع تعديل سجل migrations ودفاتر التدقيق/المال. إعداد المختبر وتدوير كلمة مرور دور قاعدة الاختبار منفصلان عن طلبات التطبيق.
- MFA أُنشئ وأُكد عبر الواجهة، ولم تُزرع بيانات اعتماد مؤكدة لتجاوز المسار. عند الاستئناف فُك سر TOTP الصناعي في ذاكرة المشغّل لإعادة الدخول؛ لا أسرار أو مفاتيح أو ملفات جلسة منشورة.
- تطابقت صفوف Binding الأصلية (1) والدفتر المالي (10) والفواتير (3) قبل الرحلة وبعدها. جدول Consent كان فارغًا؛ المثبت هنا عدم تغييره، وليس تجربة موافقة تاريخية موجودة. تبقى أدلة R05 السابقة بمصادرها دون إعادة نسبها.
- خروج كل مستخدم ألغى جلسته الحالية. أُلغي بعدها، بتنظيف منفصل عبر SessionManager، تسع جلسات صناعية من المحاولات السابقة تخص المستخدمين الثلاثة وحدهم؛ لا ندعي أن زر الخروج يلغي جميع الجلسات.
- أُغلق API والبوابة والمتصفح وPostgreSQL المملوك. لا Neon أو إنتاج أو مزود خارجي أو أثر مالي حقيقي.

## المحاولات والتصحيحات

المحاولة الأولى توقفت عند قراءة غلاف الاستجابة/محدد الحقل بعد إعداد MFA، وحُفظ فشلها وتنظيفها. المحاولة التالية أنجزت الإنشاء والمراجعة والنشر، ثم فشل عنوان الفحص العام الخاطئ. استُؤنف المحتوى نفسه دون إعادة أوامر الإنشاء/الاعتماد/النشر.

عولج انتظار pg_ctl لماسورة موروثة مع التحقق من هوية العملية وإيقافها الموثق؛ وعولج إعداد عنوان CMS القانوني: العقد يرفض المنفذ في PUBLIC_WEB_URL، لذلك استُخدم https://r14.example.invalid قانونيًا مع نقل المتصفح المحلي بمنفذ منفصل. لم يُضعف guard. كُشف العنوان الفعلي /api/v1/public/cms/pages/http-resolve بدل عنوان الفحص الخاطئ. صُحح محدد نص المحتوى لأن الاسم المتاح يتضمن القيمة الحالية. بقيت إيصالات الفشل 404/503 وفشل المحدد منفصلة عن نجاح الاستئناف النهائي الذي خلا من 5xx وأخطاء الصفحة.

لا إصلاح جديد في مصدر المنتج مطلوب من هذه الجولة؛ التصحيحات تخص أداة التشخيص وإعداد المختبر. لم نُعد المجموعات العامة أو build شاملًا أو الرحلات الناجحة غير المتأثرة.

## CI والحالة التالية

اكتمل [CI 39516645007](https://github.com/wegdangamil2022-oss/MANARATAK-First-/actions/runs/39516645007) على cbe2ff2d0e3ba881361fcbe42133af500cd4c331: الوظائف الست ناجحة، بما فيها Linux واسترجاع الحزم. هذا لا ينسب CI إلى commit التوثيق الجديد.

أُنجزت فجوة رحلة Admin العربية محليًا ضمن R09/R11. يبقى القبول الرسمي ونطاق Linux الموحد واللغة الإنجليزية والحمل الممثل وبقية العمال والتسليم الخاص والبوابات الفعلية. R14 يبقى NO_GO، ولا تشغيل promotion أو نشر أو دمج main.

نقطة الاستئناف: تسليم الوثيقة/الشهادة الخاصة من API المبني عبر مزود صناعي معزول، مع ملكية الطالب وConsent/Binding والانتهاء والسحب؛ ثم بقية عوائق الإصدار بحسب أثرها.
