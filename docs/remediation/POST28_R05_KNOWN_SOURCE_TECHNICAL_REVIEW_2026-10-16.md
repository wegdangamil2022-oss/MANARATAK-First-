## العقد المعروض، دون تطبيق على DB-U

1. يتعامل مالك الأصول مع الملف المعلوم عبر `IngestAssetUseCase.requestUploadLocator` ثم `ProcessAssetLifecycleUseCase`؛لا SQL لإنشاء AssetRecord فعال. استخدام entry الطالب الذي يسجل موافقة جديدة ليس مناسبًا لإصلاح حادث تاريخي دون موافقة طالب موثقة؛لا نصنع consent جديدة.
2. يبقى assetId والمالك مطابقين للحزمة. لا تغيير binding أو requirement/version أو هويات الطالب أو consent أو attestation. سياسة retention والتصنيف وتاريخ الانتهاء تحتاج مراجعة المالكين؛لا ننقل تاريخ retention2035 التاريخي إلى أصل جديد تلقائيًا ولا نغيّر تاريخ binding لإجباره على المطابقة.
3. مصدر PDF معروف ليس دليل CLEAN. يجب تنفيذ تحقق التخزين/checksum وفحص malware فعلي وsanitization حقيقية لنوع PDF وإعادة الفحص قبل activation. محول R04 الحالي ينظف canonical JSON فقط،ولا يجوز تقديمه كمنظف PDF. noop unavailable ليس فحصًا ناجحًا.
4. أوامر المالك تحتاج principal تطبيق محدودًا على DB-U وفق عقد هوية جديد/إعداد مراجع،دون DDL أو كتابة migration ledger؛لا تُشغَّل بدور bootstrap أو migration لإخفاء نقص الإعداد. baseline/restore الحاليان يستعملان أدوار migration المحدودة المخصصة لهما.
5. يجب تحديد delta المسموح لسجل الأصل وأثر دورة حياته وتدقيقه،وإثبات عدم تغيير وثائق الطالب والماليات. لا اعتماد عام لتغير الصفوف. تؤخذ صورة حفظ جديدة بعد المعالجة مع إبقاء نسخة before الأصلية،ثم صفر audits قبل110.
6. بعد اعتماد العقد وتوفير pipeline فعلية:109→110،العميل السابق بعد الترقية،قفل/مهلة/قطع آمن/استئناف/redeploy؛لا تتقدم هذه الاختبارات التابعة بإضافة أصل INITIATED فقط لإرضاء FK.
