# R10 — فاحص آمن وتجهيز نسخة وهدف استعادة صناعي

بدأ التنفيذ الفعلي على الفرع `feat/post28-r07-artifact-preparation`. أدلة PostgreSQL تخص `b53ce95404a96ab1fbcb45d08cdb11aacfc7a9ee`؛ الاختبار اللاحق لدخول CLI محفوظ في `fd4c4eb`. **لم تُنفذ الاستعادة، ولم تغلق R10.** [الفهرس الآلي](POST28_R10_PREPARATION_2026-10-20.json).

## الإصلاحات

أداة restore القديمة كانت تشغّل `test:database` المدمّر ثم تقرأ `snapshotId/assetReferencesMatched` من صف ادعاء. استُبدل ذلك بفاحص قراءة فقط داخل معاملة RepeatableRead: بصمات SHA-256 لجميع صفوف الجداول العامة بترتيب ثابت، والأعداد، والأعمدة والقيود والفهارس وحالات sequences، ومطابقة هوية كل أصل ACTIVE وموقعه وبصمته مع manifest الموقّع. لا تُعرض محتويات الصفوف في التقارير. هذه مطابقة نطاق الجداول العامة، وليست اعتمادًا شاملاً لوظائف SQL والسياسات والمشغلات أو تشغيل الخدمة.

أصبح manifest الذي يتضمن databaseSnapshot إلزاميًا لمسار CLI قبل أي SQL، وتُعاد مراجعة sentinel المستقل بعد الاستعادة. أُصلح دخول CLI على Windows؛ كان فحص pathname السابق قد يمنع دخول مسار التنفيذ أصلًا. أصبحت الاستعادة تستبعد ملكية المصدر وACL الخاصة به، وتستخدم فلترة TOC الموجودة لحفظ schema وpg_trgm المجهزين مسبقًا بدل محاولة إسقاطهما. لا تعديل للبوابات أو اختبارات الرفض.

تقرير الأداة يصرح الآن بأن حساب RPO القديم من وقت backup **مؤشر عمر نسخة فقط**، وليس RPO مشتقًا من أحداث مستعادة، وأن RTO المتكامل لم يُقَس. لا يجوز استعمال PASS بنيوي لإغلاق هذين الهدفين.

## الإثبات الحقيقي

أُنشئ مختبر PostgreSQL 16 جديد على القرص، وطُبقت 111 migration فيه وحده. دور `manaratak_snapshot_reader` يقرأ الجداول والسجل دون superuser/createdb/createrole/bypassrls أو CREATE على schema؛ default_transaction_read_only مفعّل.

- جرى قياس 282 جدولًا و175 صفًا، وأُخذ custom pg_dump بدور القراءة فقط. لم تتغير بيانات المصدر بين القياسين المحيطين بالـdump.
- نجحت مطابقة الفاحص للمصدر نفسه وربط أصل صناعي واحد بالـmanifest؛ رُفضت محاولة كتابة بدور القراءة، ثم كشف الفاحص تغيير بيانات صف رغم بقاء العدد نفسه.
- هذا **ليس** إثبات مطابقة بيانات بعد restore؛ `restoredDumpParityVerified=false`. ملف الأصل بايتات صناعية خام لا مستند تسليم معتمدًا أو إثبات توليد/فحص EAP.
- كشف فحص TOC أن dump المقيّد بـ`--schema=public` لا يتضمن سجل extension المطلوب للعقد. لم تُخفف الفلترة؛ أُنشئ dump كامل من المصدر الصناعي الذي لا يحوي سوى schema التطبيق، واجتاز عقد TOC. أُعيد تجهيز هذا الجزء بسبب تعديل طريقة أخذ النسخة، لا لإعادة مجموعات ناجحة غير متأثرة.
- جُهز DB-R فارغ باسم محدد في الدليل ودور `manaratak_restore_runner` محدود الصلاحيات، مع sentinel يملكه bootstrap ويملك restore role قراءته فقط. قاعدة المصدر والهدف مختلفتان داخل cluster صناعي واحد؛ هذا ليس عزل خادمين أو تجربة فقد منطقة. لم يُستخدم restore role لتنفيذ استعادة أو قراءة sentinel.
- أُوقفت المختبرات الثلاثة مع مطابقة PID ومسار PostgreSQL. قواعد المصدر والهدف وملف dump محمية خارج Git لاستكمال المراجعة، بينما نُقلت التقارير والبصمات الآمنة فقط إلى المستودع. لم تُلمس Neon أو قواعد سابقة أو main.

## الاختبارات وحدودها

نجحت 8 حالات جديدة للفاحص ودخول CLI، و16 حالة لحراس recovery، و7 حالات لعقد TOC. تمت إعادة الأجزاء المتأثرة فقط. محاولة اختيار أوسع أولى شغّلت أيضًا حالتي symlink؛ فشلتا بـEPERM لأن Windows لا يتيح إنشاء الرابط للحساب الحالي. لم يُعد تشغيلهما محليًا، ولم تُحذفا أو تضعف assertions؛ يبقى إثباتهما على Linux. نجحت جودة المصدر، والعقد المصدرّي للاستعادة. CI الجديد لا يُعد ناجحًا قبل ظهور نتيجته.

اكتملت بالتوازي نتيجة CI لإصلاحات R09 على `d4ffe62`: جميع الفحوص الـ23 ناجحة. سُجل إغلاق R09 العملي وفق توجيه المالك مع بقاء الاستثناءات الشاملة، دون اعتبارها اعتماد إنتاج.

## ما يلزم قبل خطوة الاستعادة

1. مراجعة فنية مستقلة للإصلاح والهدف المحدد. [خطة R10](POST28_ISOLATED_VALIDATION_EXECUTION_PLAN_v1.3_2026-10-16.md#r10--نسخ-احتياطي-واستعادة-قابلة-للقياس) تشترط «طرفا اعتماد مستقلان» وauthorization موقّعًا مرتبطًا بهوية الهدف والنسخة وSHA؛ لا توجد هذه الاعتمادات بعد، ولا تُختلق أسماء أو توقيعات.
2. تجهيز TLS موثوق لمسار restore (`verify-full`) وهوية المنع للإنتاج ضمن عقد الهدف، وتثبيت ثقة مفتاح سلطة التوقيع. ليست هذه البيانات موجودة لمجرد أن الهدف محلي؛ لا downgrade تلقائيًا للحراس.
3. بعد استيفاء البوابة: إعادة تشغيل المختبر نفسه مع التحقق من هويته، ثم restore إلى DB-R فقط، ومطابقة القراءة بعده. نحتاج بعد ذلك watermark مشتقًا من أحداث فعلية واستعادة خدمة وملفات لقياس RPO/RTO.

مخرجات PITR لمدة 30 يومًا والتشفير وWORM ونسخة خارج المنطقة تحتاج مزود backup معتمدًا؛ لا تغلقها pg_dump محلية، ولا تمنع تجهيز المسار الصناعي المستقل.
