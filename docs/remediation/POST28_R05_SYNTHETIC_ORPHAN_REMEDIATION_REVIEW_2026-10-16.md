# R05 — مراجعة معالجة اليتيم الصناعي قبل الترقية110

## الإجراء المعروض للمراجعة

النطاق: مختبر محلي disposable جديد فقط. لا Neon أو إنتاج أو إعادة تفسير لقرار DEC.
الحالة الحالية: **PROPOSED — NOT APPROVED — NOT EXECUTED**.
المالك التقني الذي يجب أن يراجعها: مالك StudentApplicationDocumentBinding ومالك AssetRecord؛ لا تمثل كتابة هذه الوثيقة توقيعًا مستقلًا منهما.

السجل الصناعي `2a4960c9-b4be-405a-8b21-7c3b34a5034f` يشير إلى أصل مفقود `aafb690a-1f6c-463d-8b24-3d88e9a9b5d8`.
نشأ السجل ضمن fixture معلومة على108، قبل FK/trigger الترحيل109، ويحفظ manifest سبب الإغفال. لا ملف أصلي أو دليل فحص أو checksum لهذا الأصل في manifest الحالي، لذلك لا يجوز اختلاقها أو إضافة AssetRecord فارغة لإسكات FK.

## خطة الإصلاح المقترحة

1. إبقاء المختبر الحالي كما هو كدليل رفض سليم للترقية؛ لا تعديل binding أو حذف صف أو إسقاط/تعطيل قيد.
2. إعداد نسخة جديدة من fixture manifest، تتضمن قبل الإنشاء ملفًا صناعيًا آمنًا مستقلًا، وبايتاته وSHA256 ونوعه وحجمه وهوية مالكه ومعرّفه ومسار المصدر. لا تستعمل أي ملف طالب حقيقي ولا تصف ملفًا مولدًا لاحقًا بأنه الأصل المفقود الحالي.
3. مراجعة كيفية تمثيل حادث تاريخي صناعي ذا مصدر معلوم: تحميل binding على108 مع إغفال سجل الأصل من حزمة التحميل فقط، مع بقاء ملف المصدر وبياناته وهاش manifest في الحزمة الخاصة. تثبيت SHA جديد ومختبر U/V جديد؛ لا إعادة ربط العقود القديمة.
4. backup قبل المعالجة واستعادة بنيوية منفصلة؛ ثم إنشاء الأصل **بنفس المعرف الموثق** عبر IngestAssetUseCase وProcessAssetLifecycleUseCase ومحولات مالك الأصول، مع فحص الملف وتثبيت checksum والمالك والتصنيف والاحتفاظ. لا SQL مباشر لإنشاء أصل فعال مصطنع بلا دورة حياته.
5. مراجعة استخدام أصول الوثائق بواسطة مالك الطالب: لا تغيير consent أو هوية binding أو requirement/version أو attribution. لا تجعل إعادة توفير الأصل موافقة وصول أو موافقة طالب.
6. سجل المعالجة يربط manifest/source/binding/asset ودليل المالك والفحص ومخرجات audit/outbox حيث ينفذها العقد. يجب إثبات أن delta محصور بسجل الأصل وآثار مالكه المصرح بها؛ لا سماح عام لتغير الصفوف أو الماليات.
7. أعد القياسات/backup الممثل بعد المعالجة إذا كان snapshot الحفظ النهائي يبدأ بعد المعالجة، واحتفظ بمرجع before الأصلي لتدقيق delta. لا تستبدل النسخة الأصلية أو تسقط دليل اليتيم.
8. لا تنفذ110 قبل صفْر كل audits المطلوبة، ثم تحقق من ledger110 والقيود والتطابق والعميل السابق بعد الترقية والأقفال/المهلات والقطع الآمن والاستئناف/idempotency. أي قرار تجاري يبقى عند صاحبه.

## لماذا لم ينفذ الإصلاح تلقائيًا؟

خطة Post28 R05 تشترط قائمة معالجة يراجعها المالك، وتحظر تصحيح الأيتام بالاسم أو مسحها للنجاح. طلب المستخدم استكمال العمل بسلطة مدير المشروع يتيح الإعداد والفحص والإصلاحات التقنية؛ لا يوفر ملف الأصل المفقود ولا يعد قرارًا محددًا بتغيير دليل مالك الوثائق. الإجراء أعلاه نتيجة قابلة للمراجعة، وليس ادعاءً بأن review مستقل قد حصل.
