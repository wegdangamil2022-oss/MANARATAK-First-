# تسليم أصل الطالب الخاص — إصلاح الانتهاء وإثبات API المبني

أُصلحت فجوة كانت تسمح بتسليم أصل ACTIVE/CLEAN بعد انتهاء الاحتفاظ، أو بإصدار رابط يتجاوز تاريخ الانتهاء. الإصلاح في 6fa90544d419df5afee7ae35112ae8667f578a2b، على فرع feat/post28-r07-artifact-preparation. لا تغيير في Prisma أو migrations أو مدة الاحتفاظ أو Legal Hold أو موافقة تاريخية.

## التغيير المثبت

- AssetRecord يمنع التسليم عند انتهاء التاريخ أو عدم صلاحيته، ويمنع TEMPORARY بلا تاريخ؛ تبقى PERMANENT الصريحة دون تاريخ قابلة للتسليم بشروط الثقة القائمة.
- مدة grant لا تتجاوز أقرب انتهاء للاحتفاظ أو الحقوق العامة الإلزامية. بعد رد المزود تُقرأ الحالة مجددًا وتُفحص الثقة والملكية والتصنيف والموضع والبصمة والانتهاء قبل إعادة الرابط.
- يبقى فحص القراءة الموثقة قبل IO وبعده فعالًا؛ انتهاء الاحتفاظ أثناء قراءة الملف يمنع إعادة البايتات. توجد قراءة repository إضافية واحدة لكل إصدار grant مقابل إغلاق نافذة تغيّر الحالة؛ لا نظام جديد أو مزود خارجي.

## الإثبات وسبب الإعادة

قبل الإصلاح: فشلت8 من9 حالات جديدة؛ الحالة الناجحة تثبت بقاء الأصل PERMANENT الصريح متاحًا. بعد الإصلاح وبناء Domain/Application المتأثرين فقط: نجح73 فحصًا، منها9 جديدة و64 متأثرة مباشرة تخص دورة الأصل والقراءة والثقة وDomain. TypeScript وESLint للملفات الثلاثة ناجحان. لم تُعد مجموعات عامة أو رحلات Admin أو build Web/Admin.

فشل وسيط محفوظ سببه توقف أداة التعديل لاختلاف CRLF وبقاء dist القديم؛ ثم كشف TypeScript تكرار متغير expiry أضافته الأداة أثناء الاستكمال. صُحح السبب قبل الإعادة، بلا حذف اختبار أو تخفيف assertion. بقيت النتائج الوسيطة منفصلة عن النتيجة النهائية.

بُني API وحده تشخيصيًا من SHA الإصلاح. في PostgreSQL16 جديد مع دور تطبيق محدود ومزود HTTPS محلي بتوقيع HMAC وCA صناعية محددة، ثبتت الحالات التالية:

| الحالة | النتيجة |
|---|---|
| طالب آخر يحاول منح رابط لأصل المالك | 404 قبل استدعاء منح الرابط لدى المزود |
| أصل منتهي مسبقًا | 400 قبل المزود |
| مالك الأصل يطلب الرابط وينزل PDF | 200 وبصمة SHA256 مطابقة للملف الفعلي |
| token تنزيل محرّف | 403 لدى المزود |
| طلب300 ثانية مع بقاء نحو8 ثوانٍ للاحتفاظ | رابط أقصر، ثم تنزيله200 قبل الانتهاء و403 بعده فعليًا |
| مزود يعيد مدة مفرطة | 400 دون تسليم الرابط إلى الطالب |
| سحب الأصل أثناء إصدار grant | 400 بعد فحص الحالة مجددًا؛ والطلب التالي يُرفض قبل مزود المنح |
| الخروج | إلغاء جلستي الحسابين الصناعيين |

المحاولة الأولى توقفت في إعداد role لحقل description المفقود قبل العامل وAPI؛ أُوقف PostgreSQL. المحاولة الثانية توقفت عند توقيع المزود لأن فاصل السطر في أداة المختبر لم يطابق SignedProviderHttpClient؛ حُلل السبب وصُحح دون تغيير بروتوكول المنتج. المحاولة النهائية نجحت وأُغلق API والمزود والمختبر. إيصالات الفشل والتنظيف محفوظة، ولا تجمع أعداد النجاح المتداخلة.

## حدود مهمة قبل النشر

النطاق هو أصل STUDENT خاص وعينة ثقة تاريخية صناعية معلنة، وليس دورة upload/scan/sanitize جديدة. مزود المختبر لا يدعي جاهزية malware-scanner أو asset-sanitizer. لا إعادة ادعاء قبول EAP أو R05 أو توقيع إنتاج. API يستمع loopback HTTP فقط؛ اتصال التخزين والتنزيل HTTPS بتحقق CA واسم المضيف دون تعطيل TLS عمومًا. الحزمة تشخيصية محلية، وليست artifact إصدار موحد Linux.

تطابقت Binding الأصلية (1) والدفتر المالي (10) والفواتير (3) قبل التنفيذ وبعده. جدول Consent فارغ في هذه العينة؛ ذلك يثبت عدم تغيير مجموعته الفارغة فقط. لم تُنشأ موافقة جديدة أو يعاد بناء Binding الأصلي.

إعادة الفحص تمنع **إعادة رابط جديد** بعد السحب أو أثناء رده. لا تثبت هذه الدفعة إبطال bearer URL سبق توزيعه فورًا: قد يظل صالحًا حتى انتهاء مدته لدى المزود. إذا اشترط العقد الإبطال الفوري، يلزم إثبات fencing لدى المزود أو استعمال تسليم موثق يعيد التحقق؛ هذه بوابة خصوصية قبل النشر، وليست نجاحًا مخفيًا.

ما زال بث وثيقة المراجع من API المبني مع Consent قائم وانتهائه وسحبه، وتسليم الشهادة الموقعة وpreview، والتراجع/Linux الموحد وبقية بوابات R13 غير مقبولة رسميًا. القبول الرسمي وR14 يظلان NO_GO.
