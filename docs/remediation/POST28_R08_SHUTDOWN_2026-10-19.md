# R08 — منع بدء مهام بعد stop وفرض مهلة الإيقاف

أُصلحت ثلاث حالات فعلية في المصدر `825a0b597bca7e14d95a6cc8fbf8d7bf352abdc8`، مع بقاء قبول R08 الشامل مفتوحًا:

- كان stop ينتظر المهمة الحالية ثم يبدأ خطوات Owner/Student التالية داخل الدورة؛ صارت الدورة تتوقف قبل استدعاء الخطوة التالية، دون قطع المهمة التي بدأت بالفعل.
- كان يمكن لمهمة initial tick المجدولة قبل stop أن تبدأ بعده؛ صار الفحص يعاد داخل microtask قبل استدعاء العامل.
- كانت مهلة الخادم تغطي انتظار drain، لكن تعليق monitoring flush أو إغلاق مورد بعده يمكن أن يمنع خروج العملية. صارت مهلة الـ15 ثانية مرجعًا مطلقًا: يغلق HTTP ويحاول cleanup دون انتظار غير محدود، ثم يخرج بالرمز 1 عند بلوغ المهلة. لا يُكتب نجاح لعملية غير مؤكدة؛ يتولى replay/reconciliation استعادة آثارها حسب العقود القائمة.

أُثبت الفشل أولًا لكل عيب، ثم نجحت اختبارات PollingWorkerRuntime العشرة. أُعيدت ستة فحوص shutdown/lifecycle المتأثرة مباشرة فقط. نجح TypeScript لمشروع API، وESLint بلا أخطاء مع سبعة تحذيرات any موجودة في المصدر، وفحص الأسرار.

شُغلت تجربتان بعمليات Node مستقلة مع runtime العامل الحقيقي ومهام معزولة معلقة عمدًا. انتظر stop تحرير المهمة ثم صار العامل STOPPED، ولم تُستدع خطوة أخرى، ورفضت سياسة freshness دليل STOPPED. الزمنان المرصودان بعد إشارة stop نحو 84 و87ms. هذه ليست تجربة Redis أو PostgreSQL جديدة ولا كاملة API.

شُغلت تجربة ثالثة منفصلة لجسم shutdown الفعلي المستخرج من server.ts، مع HTTP listener محلي حقيقي وmonitoring adapter لا ينهي flush ومقبض نشط. خرجت العملية بالرمز 1 بعد **15020.917ms** عند مهلة مهيأة 15000ms؛ لا ادعاء لحد زمني دقيق دون تفاوت جدولة. أُعيدت هذه الحالة الجديدة وحدها، ولم تُكرر تجربتا drain الناجحتان.

التنفيذ المحلي Windows استخدم IPC لإطلاق stop. الاختبار نفسه يختار SIGTERM حقيقيًا على Linux، وهو ضمن الاكتشاف التلقائي لاختبارات Node، لكن **لم يُرصد نجاح Linux بعد**. لا تتغير المهلة الإنتاجية إلى مهلة قصيرة لإظهار النجاح. فحص موارد built API الفعلية وDB/Redis أثناء التجاوز يظل مطلوبًا.
