# AI and student tools administrative workspaces

## Scope and source baseline

Implemented together on `feat/ai-student-tools-workspace-20261027`, from main `533264705c07c02198841b713c906871d6f64675`.
This release organizes the existing AI control plane and student tool registry. It does not implement the 79 planned tools, configure external credentials, run paid inference, or install data in an existing database.

The registry source contains 83 definitions: four implemented handlers and 79 planned definitions. Database totals are read from the actual repository; the UI never substitutes source counts or sample records when the database is empty or inaccessible. Ten administrative tool identities are protected independently of their editable category.

## Navigation and presentation

AI has six workspaces: overview, operations, providers and models, capabilities and prompts, knowledge and automation, and governance and quality. All 18 legacy subsection links remain usable. Daily provider, model, price, capability, routing, consumer, safety, index and incident settings use labelled forms. Complex workflow definitions and evaluation datasets retain the existing advanced JSON editor and server validation.

Student tools has four workspaces: library, releases, usage, and quality. Every tool has overview, content, access, release, testing, and execution/audit tabs. The library supports server pagination, source status, category, audience, lifecycle, execution type and sorting. Its implemented label explicitly describes source implementation rather than production availability.

Both use the existing reference-data and certificate styles: Cairo, 13px body, 22px title, 14px main navigation, 13px subsection navigation, and compact 12px secondary text. Selected navigation and primary controls use navy with gold icons. AI's six sections occupy equal three-column rows on desktop and two columns on smaller screens; the tool navigation adapts to the number of visible permitted sections. Registry editing opens its second column only after selecting a record. Forms, metrics and empty states use compact spacing; certificate empty messages are 12px. Cairo is explicitly enforced throughout the admin workspace. Owner links require the corresponding permission. Existing canonical university/scholarship data remains owned by those sections.

## Mutation and privacy boundaries

- Tool access, feature flags and rate limits are one strict versioned API command with an expected revision. They cannot partially succeed as separate client writes. Unsupported regional policies are preserved and rejected instead of silently erased.
- Release decisions remain bound to the version snapshot, revision, approval status and expiry. The server enforces independent authors/reviewers and readiness; configuration checks are not answer-quality evidence.
- Tests use typed forms for GPA, university comparison, motivation letters and scholarship recommendations. They require synthetic-input acknowledgement, additional approval for AI costs, and run-test permission. Administrative test usage is separate from student usage.
- A network failure freezes test input and offers only an identical retry with the same idempotency key. RUNNING and UNKNOWN_OUTCOME receipts direct the operator to execution status. Navigation is protected while a test is in flight.
- After a tool write, the UI rereads the server. Unconfirmed state blocks another write until reload. Unsaved configuration prompts before navigation.
- Admin execution projections allow only operational fields; they exclude student input, private output, requester/input/output hashes and arbitrary metadata. Detail access is scoped to the selected tool and requires execution-view permission.
- AI emergency stop is a one-way audited command requiring safety permission, a reason, and the expected update timestamp. It disables admission of new requests; it does not claim to cancel running calls or disable deterministic tools. Re-enabling continues through the existing governed configuration process.
- Empty telemetry samples display N/A. Technical success uses completed/(completed+failed), excluding running/blocked/unknown requests; it does not measure answer quality.

## Acceptance and remaining runtime boundaries

The focused suites cover navigation, Arabic/English rendering, stale responses, duplicate requests, atomic access policies, internal audience, safe projections, owner-scoped detail, and emergency-stop authorization. The source closure gate covers all 65 existing AI/tools invariants. Builds, static checks and the platform regression suite are recorded separately from runtime acceptance.

Original database startup must use the existing application role, trusted TLS roots and existing encrypted MFA key; no migration, seed or account modification is part of this change. A missing schema or registry is a reported deployment prerequisite, not permission to create it. Runtime verification requires the normal authenticated user session. Provider health and paid output quality remain unverified until separately authorized real executions; no UI status may claim that source tests prove them.

The typography/layout refinement passed 40 tests across eight AI, tools and certificate suites on Node 22, admin TypeScript checking and the admin production build. Lint has no errors; the existing version-history cleanup-ref warning remains. Windows visual inspection could not run because the Computer Use native pipe was unavailable; source, component tests and HTTP asset verification are not a substitute for an authenticated visual check.
