### 05.02 — بطاقة التخصص في القائمة: ما هو موجود فعلًا

`MajorAdminPage.tsx` يعرض بطاقات ثلاثًا في الصف على الحاسوب، وعمودين بالقياسات الوسيطة، وواحدة على الجوال. داخل البطاقة توجد العناصر التالية:

| العنصر | الحالة المثبتة | القرار |
|---|---|---|
| الدرجة العلمية | Badge واضح بـLucide GraduationCap | **الإبقاء** |
| كود التصنيف أو المعرّف العام | يظهر إن وجد | الإبقاء؛ تمييز رمز التخصص العام من رمز نظام ISCED حتى لا يختلطا |
| اسم التخصص العربي أو الاسم الأساسي | عنوان رابط للفتح | الإبقاء؛ Cairo 15px وLine Clamp مع إظهار الكامل عبر Tooltip/صفحة التفاصيل بإتاحة مناسبة |
| الاسم الإنجليزي | يظهر عندما يوجد | الإبقاء؛ اتجاه `ltr` فقط للنص لا للبطاقة كلها |
| الكلية | يظهر أو «غير محددة» | الإبقاء؛ لا تعرض «جامعة» أو «كلية» مختلقة من اسم السجل |
| المجال الأكاديمي | يظهر أو «غير محدد» | الإبقاء |
| حالة النشر/المراجعة | Badge | الإبقاء؛ الحالة تخص ملف الدرجة الظاهر عند تعدد الملفات لا الجذر بصفة غامضة |
| اكتمال الهوية | Badge مستقل | الإبقاء؛ التأكيد بأنه **اكتمال الهوية فقط** لا اكتمال المحتوى التفصيلي |
| نسخة منشورة | Badge إذا كان `currentPublishedVersionId` متاحًا | الإبقاء مع تجنب تكرار معنى حالة النشر؛ توضيح وجود نسخة منشورة حتى إن توجد مسودة جديدة |
| تاريخ آخر تحديث | موجود | الإبقاء مع الوقت/المنطقة الزمنية عند الحاجة، وعدم الادعاء بتاريخ عند غيابه |
| فتح التفاصيل | زر ظاهر | الإبقاء؛ لا تضع الأوامر الحساسة جميعها داخل البطاقة |
| جدول بديل | موجود بسبعة أعمدة | الإبقاء، وتوحيد الدلالات بين الجدول والبطاقة |

**المفقود الجوهري** هو بيان حالة **المحتوى التفصيلي لهذا المستوى**، بعيدًا عن اكتمال الهوية. مقياس حقيقي على مستوى `MajorProfile` ونسخة المحتوى الأخيرة يميز: `لا محتوى مستورد` / `محتوى غير مكتمل` / `بحاجة لمراجعة` / `جاهز وفق حارس النشر` / `تعذر التحقق`. لا تستنتج الاكتمال من مجرد `sections.length` أو وجود `currentPublishedVersionId`. إن كان عدد الأقسام الإلزامية المكتملة موثوقًا، اعرض صيغة صغيرة `المحتوى: X/Y` ويجب ربط مقام Y **بقالب الدرجة نفسها وبقواعد بوابة المراجعة**، لا عدد بطاقات واجهة العرض، مع بيان معنى الرقم؛ إن لم تتوفر بيانات موثوقة، اكتفِ بحالة غير متاحة.

**مقترح توزيع بطاقة نهائي محافظ:** صف أعلى الدرجة + الرمز؛ الاسم العربي/الإنجليزي؛ الكلية والمجال؛ صف حالتي «النشر» و«الهوية»؛ صف حالة «المحتوى» عند توافر الدليل؛ أسفلها تاريخ التحديث وزر «التفاصيل». لا تضف صورًا زخرفية، إحصاءات وظائف غير مثبَتة، أو أزرار تعديل/نشر/حذف إضافية على البطاقة. لا تضخم ارتفاعها.

### 05.03 — صفحة القائمة والفلاتر: جرد الموجود والملاحظات

موجود بالفعل: إنشاء تخصص جديد، «كل التخصصات»، «كتالوجات المصدر»، «تخصصات جديدة»، مركز الاستيراد، بطاقة/جدول، البحث بالاسم/الكلية/الرمز، الفلاتر: الدرجة والحالة والاكتمال والتصنيف والمجال الأكاديمي والتصنيف الفرعي والكلية، إعادة ضبط، Pagination بحد 24، وحالات خطأ وفراغ.

الأعمال المطلوبة دون إعادة البناء:

1. **الإحصاءات الملخصة:** `stats.published`, `needsReview`, `complete` تسقط إلى حساب سجلات *صفحة الـ24 الحالية* عندما يغيب `data.stats`، وقد تختلف قيم «إجمالي التخصصات ضمن النتائج» من حجم/أساس عدّ حالات أخرى. الواجهة تميّز «في الصفحة» حاليًا؛ الأفضل API مجموعات كاملة حسب الفلاتر يعيد لكل مقياس تعريفًا واضحًا ونطاقه، مع الحفاظ على صدق «في الصفحة» عند الاضطرار لاستخدام عينة. لا تُضرب نتيجة الصفحة في عدد الصفحات.
2. **الفرز المفقود في واجهة القائمة:** أضف فرزًا خادميًا مدعومًا، مثل الاسم العربي/الإنجليزي، الأحدث تعديلًا، الدرجة، حالة النشر. لا تكتفِ بفرز السجلات الـ24 محليًا. راجع إمكانيات API أولًا.
3. **الربط بين الفلاتر والرابط:** احفظ الفلاتر والصفحة ونمط العرض في URL بطريقة مستقرة تسمح بالعودة من التفاصيل إلى القائمة بنفس نطاق العمل، ولا تمس `view=new/catalog` أو سياق `profileId`.
4. **خيار كتالوج المصدر:** إبقاء بعض فلاتر التصنيف والكلية معطلة فيه مفهوم؛ اشرح بوضوح الفرق بين مصدر مرشح وتخصص معتمد، وإزالة الفلتر المعطل من معايير النتيجة بدل إظهار أرقام مربكة.
5. **حالات غياب البيانات:** لا تعرض 0 عند فشل API أو خلل صلاحيات. لا تدع البحث السريع يولّد استعلامات غير محدودة؛ debounce والإلغاء وفهرسة خادمية.
6. **التمييز بين وحدة العد:** هل `data.total` عدد جذور تخصصات فريدة أم ملفات درجات `profiles`؟ بما أن العناصر قد تستخدم `profileId`، عرّف وحدة العد في API والواجهة قبل عرض «إجمالي التخصصات»، وافصل عدد الجذور عن عدد الملفات إذا لزم.

### 05.04 — خمسة تبويبات تفاصيل التخصص: الإبقاء على ترتيب المالك

احتفظ بالملاحة الأفقية الواضحة والمسافات ومقاسات Cairo وألوان/أيقونات التبويبات الحالية؛ لا تحوّلها إلى قائمة جانبية أو مربعات مطوية متداخلة:

1. **البيانات الأساسية** — هوية التخصص باللغة العربية/الإنجليزية، الدرجة، الرمز، الكلية، المجال/التخصص الدقيق، التصنيف، الحالة، وصف الطالب، والمعلومات الإضافية ذات الصلة.
2. **المحتوى التفصيلي** — مجموعات القالب الرسمية لكل مرحلة أكاديمية، كتل المحتوى الفرعية، التحرير والمراجعة.
3. **التصنيف والدرجات** — ملفات الدرجات العلمية التابعة للجذر، وخرائط التصنيف المعتمد.
4. **العلاقات والمرادفات** — الأسماء البديلة وعلاقات التخصصات؛ قراءة أسماء واضحة بدل IDs خامة.
5. **النسخ والمصادر** — النسخ حسب الملف/الدرجة، المصادر والتواريخ والحالة، ومقارنة النسخ/التدقيق عند الحاجة.

**مشكلة تنظيمية مؤثرة:** `FellowshipAuthoringPanel` يُرسم **خارج شرط التبويب** داخل صفحة التفاصيل ويتضمن `<details>` افتراضيًا، بينما `MajorGovernanceWorkspace` في `<details id="major-publication">` منفصل **قبل التبويبات**، وعناصر مهمة أخرى في `details` تقنية. انقل إجراءات المراجعة/اعتماد الجاهزية والنشر الظاهرة إلى منطقة الأفعال الصحيحة، وأدرج أدوات الزمالة في تبويب المحتوى/النسخ المناسب **عندما يكون الملف زمالة أو يجري إنشاؤه عمدًا**. تُترك التفاصيل التقنية المتقدمة/مقارنة نسختين وتاريخ التدقيق خلف توسع اختياري فقط.

### 05.05 — القوالب الأصلية بحسب الدرجة؛ لا تعدّلها

الواجهة تحتوي تعريفات `BACHELOR_MAIN_SECTIONS` = **10 مجموعات رئيسية**، `MASTER_MAIN_SECTIONS` = **16 مجموعة**، `DOCTORATE_MAIN_SECTIONS` = **19 مجموعة**. **هذه مجموعات واجهة مجمعة وليست بالضرورة عدد أقسام المصدر الأولية أو حقول بوابة المراجعة**؛ لا تستخدمها مقامًا لقياس تغطية دون فحص خرائط المحتوى والقالب الرسمي. في الكود: البكالوريوس مفتاح 01…14، الماجستير 01…25، الدكتوراه 01…26 مع دمج بعض المفاتيح في مجموعة واحدة.

- **البكالوريوس:** الهوية، النبذة، ماذا يدرس الطالب، المهارات، المسارات الدقيقة، مجالات وفرص الوظائف، الدراسات العليا، المشابهة، التنبيه المهني.
- **الماجستير:** الهوية، النبذة، أنواع البرنامج، خلفيات القبول، المتطلبات الاستدراكية، ماذا يدرس الطالب، المسارات، التخرج، المهارات المتقدمة، العمل، اللاحق، المشابهة، علاقة البكالوريوس، التنبيه، المصادر.
- **الدكتوراه:** الهوية، طبيعة البرنامج، الأنواع، مسارات الدخول، المراحل، المقررات والمعرفة المتقدمة، البحث، التأهيلي، المقترح، الأطروحة، الإشراف، متطلبات النشر والتدريس، المهارات، العمل واللاحق والمشابهة والتنبيه والمصادر.
- **الزمالات:** **لديها قالب مرجعي رسمي قائم من 18 قسمًا مرقمًا** في `workspace/phase-10-major-catalogs/MANARATAK_Fellowships_By_Professional_Domains_v1.0.md` تحت «القالب المعتمد لكل زمالة». لا يُختَرع قالب آخر ولا تُختزل أقسامه إلى ستة. يوجد أيضًا `MAJOR_REVIEW_TEMPLATE.FELLOWSHIP` ذو **6 مفاتيح تحقق تقنية** (`identity`, `overview`, `requirements`, `benefits`, `academic_notice`, `sources`) لأغراض دورة اعتماد النسخ؛ **هذه ليست بديلًا عن الأقسام التفصيلية الـ18**. في الواجهة ترجع `groupSectionsByCanonicalDefinitions` مجموعات فارغة للمستوى `FELLOWSHIP`، فتظهر محتويات ذلك المستوى غير مصنفة/للقراءة فقط في العرض العام، بينما `FellowshipAuthoringPanel` يوفّر تحريرًا منفصلًا. المطلوب تحسين عرض/تحرير **القالب الموجود** وربطه بتغطية الاعتماد الصحيحة فقط بعد التحقق من شكل بيانات النسخ وخرائط المطابقة، **بلا تعديل للقالب أو اختراع محتوى**.

### 05.06 — ناقص رئيسي في المحتوى: «أضف محتوى لهذا القسم»

حاليًا يعرض تبويب المحتوى قسمًا بلا `blocks` برسالة «لم يُضف المحتوى لهذا القسم بعد» **ولا يوجد زر واضح لإضافة كتلة**. زر «تعديل» يظهر فقط داخل كتلة محفوظة مسبقًا؛ الأمر يجعل التصحيح اليدوي لسجل مستورد ناقصًا مربكًا.

**المطلوب:** داخل كل قسم فارغ وفي ترويسة كل قسم يقبل إضافة كتل وفق القالب، زر ظاهر `إضافة محتوى`/`إضافة قسم فرعي` مع استمارة محدودة لعنوان القسم/المفتاح/المحتوى/اللغة وحالة المراجعة، ومصدر التغيير، ثم حفظ حقيقي عبر واجهة المالك والنسخة الصحيحة. لا تنشئ مفتاح قسم من فراغ ولا تسمح بكتلة مكررة على نفس `profileId + versionId + locale + sectionKey`. إن كانت API لا تسمح بالإنشاء، استكمل use case المدقق بدل إظهار زر لا يعمل.

عند وجود كتلة محفوظة: حافظ على **عرض ثم تعديل/حفظ/إلغاء** كما هو؛ أضف إدخال المبرر ضمن النموذج المرئي لا `window.prompt` الذي يمكن إلغاؤه أو إغفاله، مع إبطال/تعطيل الحفظ في غياب مبرر مطلوب وصلاحية ونسخة قابلة للتعديل. لا تسمح بإزالة أدلة المصدر نتيجة حفظ تعديل محتوى غير مرتبط بها.

### 05.07 — «أقسام إضافية مسجلة»: محتوى غير معيَّن يحتاج مراجعة

`unassignedBlocks` يعرض محتوى غير مصنف ضمن المجموعات الرسمية، **لكن في العرض الحالي لا توجد فيه أزرار تعديل وحفظ، بينما الأقسام المعيَّنة قابلة للتحرير**. لا تُسقط البيانات غير المصنفة ولا تحوّلها تلقائيًا إلى قسم أقرب اعتمادًا على الاسم فقط.

المطلوب: مساحة واضحة باسم «محتوى يحتاج تحديد القسم» مع `sectionKey`, `sourceMainTitle`, `sourceLevel`, `locale`, `profileId`, `versionId`, المصدر وحالة المراجعة إن توفرت. تسمح لمراجع مخول باختيار المجموعة المعتمدة وطلب إعادة الربط/التصحيح مع إثبات قبل/بعد، والاحتفاظ بالمحتوى الأصلي والمرجع. لا تعرض «بيانات جديدة للمستخدمين» دون اعتماد. إذا تعذر حسم المجموعة، تبقى محفوظة وغير مطروحة ضمن «مكتمل».

### 05.08 — سلامة حفظ الكتل والمستويات والنسخ

- يوجد حفظ كتلة واحدة، وحفظ جميع الكتل المعدلة، و«إلغاء»، ورسالة تحذير عند مغادرة المستوى مع تعديلات؛ هذه وظائف **موجودة وجيدة** نحافظ عليها.
- حاليًا `handleSaveBlock` و`handleSaveAllDirtyBlocks` يطلبان سبب التعديل بواسطة `window.prompt` قبل PUT. استبدله بحقل مدقق ظاهر مع سياق القسم/النسخة، وتحكم رفض خروج واضح، ورسائل خطأ داخل الصفحة؛ لا تعرض نجاحًا عند فشل readback.
- عمليات الحفظ تعتمد `versions[0]?.id` ضمنيًا بوصفها نسخة العمل؛ يجب تحديد النسخة المسموح بتحريرها **من حالتها الفعلية**، لا أول عنصر بالضرورة، والتأكد أن `versionId` و`profileId` و`revision`/ETag متطابقة. تعامل مع 409/412 بتعارض مرئي يحفظ مسودة المستخدم ويمنع الكتابة على نسخة بديلة.
- لا تسمح بتحرير نسخة منشورة ثابتة دون إجراء «إنشاء نسخة عمل» الرسمي إن كانت سياسة النظام تتطلبه. راجع قيود الخادم وصلاحيات `admin:majors:manage/review/publish`، وحافظ على حدث Audit.
- `handleSelectLevel` يحذر عند مغادرة مستوى، لكن يجب حماية الانتقال إلى صفحة أخرى والرجوع والتنقل بين تبويبات التحرير وكل الأزرار ذات الاستبدال/التحديث التي قد تفقد المسودة. لا تعطل كل التنقل بلا سبب حين لا توجد تعديلات.
- التعديل على الجذر (`displayName`, `collegeOrFaculty`, `academicFieldOrDiscipline`) يجب أن يحدد ما يخص الجذر وما يخص ملف الدرجة النشط، دون تعميم تغيير الاسم على درجات أخرى دون وضوح.
- زر «تجاهل وإلغاء التعديلات» والتحديث عند وجود تغييرات يجب طلب تأكيد واضح واستعادة المصدر الحقيقي فقط، لا فقدان مسودات أخرى، مع تجربة هاتف مناسبة.
- تحديث محتوى Markdown يجب أن يحافظ على العناوين والجداول والقوائم ولا يُظهِر وسومًا خامًا خطيرة؛ اختبر نصوص عربية وإنجليزية وحروف خاصة ومحتوى كبيرًا.

### 05.09 — النشر وإجراءات المراجعة: أفعال مهمة غير مخفية

الموجود في الكود: زر «المراجعة والنشر» يفتح قسم `<details>` منفصلًا، وفيه `MajorGovernanceWorkspace` يحتوي «اعتماد محتوى النسخة»، «إنشاء نسخة عمل»، «اعتماد الجاهزية للنشر»، «نشر النسخة المعتمدة»، «إلغاء النشر». ويوجد زر نشر آخر في الهيدر مع تحقق UI للجاهزية والصلاحية، وهذا قد يؤدي إلى تكرار قرارات النشر أو إرباك نطاق الزر.

**القرار:** منطقة «حالة المستوى الحالي وإجراءات النشر» ظاهرة مباشرة أعلى التبويبات أو ضمن تبويب إداري واضح غير مطوي؛ تعرض الحالة الحالية، اكتمال الهوية، اكتمال المحتوى، نتيجة البوابة، الموانع ومصدر القرار. اعتمد **أمر نشر واحد أساسي** و**أمر إلغاء نشر واحد** للملف النشط، مع بقية خطوات المراجعة ظاهرة فقط عندما تكون مناسبة للحالة والصلاحية. إظهار الزر المعطل مع سبب محدد أفضل من اختفائه المفاجئ إذا كان مهمًا للعمل. اجعل إنشاء نسخة عمل مسارًا مستقلًا وواضحًا عند الحاجة.

افحص إن كانت **الأرشفة والرفض والاستعادة** مدعومة في Owner API للملف/التخصص قبل وصفها «ناقصة بالكامل»؛ الظاهر في واجهة التفاصيل التي تمت مراجعتها لا يوفر لها أزرارًا صريحة. إذا كانت مطلوبة للـworkflow ودعمها موجود أو يحتاج استكمالًا، نفذها بالصلاحية والتأكيد والتدقيق وحماية علاقات الجامعة والمنح. **لا تضف حذفًا نهائيًا للتخصص مرتبطًا بسجلات أخرى.**

### 05.10 — التصنيف والدرجات: ما يجب إظهاره وأدوات ناقصة

الموجود: ملفات الدرجة متعددة تحت جذر واحد، اختيار درجة مستقلة، `ReviewedGraphEditor` لتصنيف تخصصات معتمد، وقراءة خرائط التصنيف.

المفقود/ما يستحسن إصلاحه:

- عرض اسم ورمز التصنيف المعتمد ومساره/هرميته بوضوح بدل `taxonomyNodeId` خامة في بطاقات الخريطة؛ الإبقاء على المعرّف التقني في تفاصيل ثانوية.
- إظهار هل العلاقة `PRIMARY` أو ثانوية، ومن راجعها ومتى عندما يوفر الخادم الدليل، وعدم الخلط بين حقل `classificationCode` المحلي و`ISCED-F` أو عقدة تصنيف عامة.
- عند التنقل بين ملفات الدرجات، تمييز المستوى النشط بصريًا، وإظهار حالة المحتوى/النسخة لهذا المستوى؛ تجنب فتح الدرجة دون تغيير البيانات المعروضة فعليًا.
- دعم تدفق واضح لتصحيح درجة مرتبطة على نحو خاطئ **بمراجعة مرجعية**؛ لا تنشئ درجة جديدة اعتمادًا على تشابه النص، ولا تفكك الجذر المشترك للتخصص من تلقاء نفسك.

### 05.11 — العلاقات والمرادفات: لا تترك المستخدم أمام معرفات خامة

الموجود: قائمة أسماء بديلة، قائمة علاقات، وواجهة إنشاء/مراجعة الأسماء والعلاقات والتصنيف داخل `MajorGovernanceWorkspace` المختبئ تحت **مراجعة ونشر** ثم تفاصيل داخلية أخرى. لوحة استخدام `MajorConsumerUsagePanel` تقرأ العلاقة بالجامعات والمنح ولكنها في «معلومات تقنية» مطوية.

المطلوب: داخل تبويب **العلاقات والمرادفات** نفسه تظهر بيانات العلاقات بأسماء التخصصات المرتبطة ودرجاتها ونوع العلاقة، مع رابط واضح للتخصص الهدف، وعدم الاكتفاء بـ`targetMajorId`. **إضافة اسم بديل** و**إضافة علاقة** و**تعديل/إنهاء علاقة** إذا دعمه الخادم، تظهر أمام المخوّل في سياق التبويب دون فتح صندوق مراجعة النشر ثم صندوق آخر. حافظ على حالة `REVIEWED` والدليل والـAudit ولا تنشئ روابط آلية من المحتوى الحر.

«أثر التغيير واستخدام التخصص» يبقى قسمًا ثانويًا يمكن فتحه عند عمليات حساسة مثل تعديل الهوية أو إلغاء النشر، مع تنبيه ظاهر عند وجود روابط منشورة فعلية حتى لا يحذف قرار إداري مسارًا من جامعة أو منحة. اقرأها من أصحابها، مع الصلاحيات وحدود التصفح، ولا تزعم أن عدد الروابط هو عدد الجامعات أو المنح الفريدة.

### 05.12 — النسخ والمصادر والمقارنة والتدقيق

الموجود: تاريخ نسخ في تبويب «النسخ والمصادر» مع الحالة والمصدر والتاريخ، ومقارنة في `MajorGovernanceWorkspace`، وسجل audit للمصرح له.

النواقص: لا تكتفِ بعرض `ver.id` و«ملف المصدر»؛ وضّح رقم النسخة والحالة والدرجة النشطة واللغة وتاريخ الإضافة/التعديل والنشر ومدى المراجعة إن كانت حقولها موجودة. لا تعتمد على fallback `حديثًا` عند غياب تاريخ؛ اكتب «التاريخ غير متاح». لا تعتبر «idx===0» دليلًا قطعيًا أن الإصدار الحالي منشور؛ اعتمد علاقات نسخ/حالة فعلية. ضع رابط «قارن بنسخة» في تبويب النسخ حيث يتوقعه المسؤول؛ مقارنة المحتوى المطولة نفسها يمكن أن تكون في مساحة ثانوية لأنها ليست إجراءً يوميًا. سجل القرارات والتدقيق للمرخص فقط، دون العبث بتاريخ النسخ.

### 05.13 — الزمالات: احفظ القالب الموجود واجعل تحريره واضحًا

**تصحيح مؤكد بعد مراجعة المصدر:** الزمالة **ليست بلا قالب**. الملف الرسمي `workspace/phase-10-major-catalogs/MANARATAK_Fellowships_By_Professional_Domains_v1.0.md` يعرّف قالبًا من **18 قسمًا تفصيليًا** (الهوية؛ الطبيعة؛ النوع؛ الفئة؛ المؤهلات؛ المدة؛ مكونات التدريب؛ الكفاءات؛ المسارات؛ الإشراف؛ التقييم؛ الشهادة؛ الترخيص؛ العمل؛ العلاقة بالإقامة/البورد/الدكتوراه؛ المشابهة؛ التنبيه المهني؛ المصادر). لا تُستبدل البنية ولا تُضاف حقول من عندنا. المفاتيح الستة في `MAJOR_REVIEW_TEMPLATE.FELLOWSHIP` تخص **فحص التغطية في سير الاعتماد** ولا تختزل المصدر المرجعي.

يوجد محرر `FellowshipAuthoringPanel` يتطلب درجة معيارية ورابط مصدر وبصمة SHA-256 ومبررًا؛ ويدعم محتوى نسخة زمالة، لكنه يظهر في `<details>` خارج التبويبات. المطلوب إظهار تحرير الزمالة داخل المسار الصحيح ببطاقات وفق القالب الأصلي، مع كشف الربط بين الأقسام التفصيلية وتمثيلها المعتمد تقنيًا قبل التنفيذ، وتجنب عرضه كإجراء إنشاء عام على كل تخصص. **لا تنشئ قالبًا بديلًا، ولا تُسقط البيانات، ولا تغيّر البكالوريوس/الماجستير/الدكتوراه.**

**جرد ملفات المصدر الفعلي (24 أكتوبر 2026):** قائمة الكتالوج تحوي 329 رمزًا `FEL-0001`–`FEL-0329`، وأول عشرة (`FEL-0001`–`FEL-0010`) **موجودة كصفوف كتالوج بأسمائها وخصائصها المختصرة**. لكن دليل الملفات المتتبعة تحت `workspace/phase-10-major-detail-dossiers/` لا يضم مجلد `fellowship`، ولا عُثر تحت `workspace` على ملفات تفاصيل فردية مستقلة باسم FEL؛ لذلك **لا يُدّعى أن تفاصيل العشرة مكتملة أو أن 329 ملفات محتوى مكتملة في المستودع**. إن كانت مسودات العشرة محفوظة خارج هذا الفرع/في مكان آخر، استلمها أولًا وافحصها دون اعتبارها مستوردة. ولا تستنتج من وجود تعريف في المصدر أنه سُجّل بقاعدة البيانات.

**ملاحظة عقد يجب مراجعتها دون تعديل متسرع:** قواعد الكتالوج الأولي تشير إلى زمالة كمجال مهني منفصل عن الدرجة الأكاديمية، في حين ينفذ عقد B10a الإداري ملف `FELLOWSHIP` على `MajorLevelProfile` تقنيًا. حافظ على عقد التشغيل المعتمد عند البرمجة ووثق التمايز بين الصنف المفهومي ومُمثّل البيانات، ولا تجري ترحيلًا أو تغيير ملكية تلقائيًا.

### 05.20 — مركز اكتشاف التخصصات الجديدة: الهدف والتصميم والتنفيذ المطلوب (قرار المالك، v1.10)

**الهدف الذي اعتمده المالك بوضوح:** زر «تخصصات جديدة» أعلى صفحة إدارة التخصصات هو **صندوق وارد لاكتشاف أسماء التخصصات غير المعروفة للكتالوج المعتمد ودرجاتها العلمية فقط**. عند ظهور برنامج جامعي أو تخصص منحة أو شرط تخصصي في المنحة ولم يتمكن النظام من ربطه بمعرف Major موجود، يظهر هنا **اسم التخصص + الدرجة العلمية الصحيحة إن كانت موثقة**. بعد ذلك **المالك بنفسه** يبحث عن محتوى التخصص، ويكتب أو يستورد تفاصيل أقسامه لاحقًا. **Codex لا يبحث عن تفاصيل التخصص، لا يُنشئ أو يملأ أقسام محتوى، لا يصدر معلومات أكاديمية بالذكاء الاصطناعي، ولا يضيف تخصصًا معتمدًا أو ينشره آليًا.**

#### أ. نتيجة تدقيق الكود الفعلي قبل إضافة المواصفة

- `apps/admin/src/pages/MajorAdminPage.tsx`: زر «تخصصات جديدة» موجود في شريط الأعلى، يحفظ `view=new` في الاستعلام ويعرض `MajorOwnerImportWorkspace` و`NewMajorCandidatesPanel`. شارة عدد المرشحين موجودة، لكنها تُقرأ مرة واحدة في `useEffect` عند فتح الصفحة؛ وقد تتأخر عن تغيرات الطابور حتى إعادة فتح الصفحة.
- `apps/admin/src/components/NewMajorCandidatesPanel.tsx`: يجمع المرشحين من API، ويوفر بحثًا وفلتر المصدر وصفحات، وعرض الاسم، والدرجات المحتملة، والمصادر؛ لوحة مراجعة جانبية تستطيع مقارنة مرشح بتخصص موجود، واعتماد الهوية وربط المصدر، أو الربط بالموجود، أو رفضه مع مبرر. هذه وظائف **موجودة ينبغي الحفاظ عليها**، ولكن واجهة القائمة الحالية مزدحمة بالنسبة إلى هدف المالك البسيط.
- `packages/domain/src/majors/NewMajorCandidate.ts`: مرشح الاكتشاف ليس Major منشورًا؛ فيه `candidateKey`, `sourceDigest`, أسماء المصدر ومراجعه ودرجات محتملة ومعلومات التتبع، ويتطلب قرارًا بشريًا.
- `packages/infrastructure/src/majors/PrismaNewMajorCandidateRepository.ts`: القراءة من ثلاثة مصادر فعلية: `UniversityAcademicProgram` غير المطابق، و`ScholarshipMajorTarget` غير المحسوم، و`ScholarshipEligibilityItem` الخاص بالتخصص. لا تسحب كل الكلمات من نصوص المنح أو وصف الجامعة. المصدر الخام يبقى محفوظًا عند مالكه. الطابور يستخدم تجميعًا بالاسم المطبّع وحده؛ يجب التحقق من الدرجات قبل اعتماد هذا التجميع للعرض والربط.
- `apps/api/src/presentation/api/router/MajorAdminRouter.ts` و`packages/application/src/majors/use-cases/AdminMajorUseCases.ts`: هناك APIs للمقارنة والاعتماد والربط والرفض، مع فحص درجة وتصنيف وصلاحيات وبصمة مصدر وrevision عند ربط الموجود. **لا تُنشئ هذه المواصفة مسارًا بديلًا لهذه الضوابط**، ولا تنقل مراجع جامعة/منحة إلى مالك التخصص بدون قرار إداري صريح.
- **فجوة مثبتة:** واجهة الاعتماد الحالية تتيح اختيار `BACHELOR` و`MASTER` و`DOCTORATE` فقط؛ الـAPI الحالي للمرشحين يقبل هذه المستويات الثلاثة ويمنع `FELLOWSHIP` في مسار الإنشاء العام. لذلك أي مرشح زمالة محتمل يُعرض في الاكتشاف بدرجته إن كانت معروفة، لكن لا يمرر إلى اعتماد غير مدعوم أو يسلك مسار إنشاء خاطئًا؛ يستخدم عقد الزمالة المخصص الموجود بعد تحقق Codex من توافقه.

#### ب. ما الذي يحتويه القسم — الواجهة المعتمدة

1. **رأس صغير واضح:** العنوان «تخصصات جديدة»، وتحت العنوان سطر توضيحي مختصر: «تخصصات لم تُطابَق مع قائمة التخصصات المعتمدة بعد. ابحث عن تفاصيلها وأضفها بنفسك لاحقًا». بدون فقرات شرح طويلة.
2. **عدد المرشحين غير المحسومين** كعدد خادمي حقيقي، مع علامة حالة جلب/خطأ عند تعذر القراءة. لا تعرض `0` إذا تعذرت قاعدة البيانات أو API. يمكن إبقاء الشارة على زر «تخصصات جديدة» وتحديثها بعد أي مراجعة أو جلب، من غير إعادة تحميل الصفحة كلها.
3. **بحث بالاسم** بالعربية والإنجليزية (عند وجود أحدهما في المرجع)، للعثور على المرشح، مع debounce وإلغاء الطلب السابق وفلترة خادمية حقيقية على كامل الصفحات؛ زر مسح البحث.
4. **فلتر الدرجة العلمية:** «كل الدرجات / بكالوريوس / ماجستير / دكتوراه / زمالة / غير محددة». يجب أن يكون مبنيًا على قيمة مدققة، لا اشتقاقًا من الاسم أو من جميع درجات المنحة بلا رابط مؤكد. إن كان Backend لا يدعم فلتر الدرجة فاستكمله بعد التحقق من البيانات. لا تجعل الزمالة تمر من مسار اعتماد بكالوريوس افتراضي.
5. **بطاقات اكتشاف بسيطة ومتواضعة:** تحتوي **اسم التخصص بالضبط كما ورد في المصدر** وشارة **الدرجة العلمية**. لا تضع على البطاقة وصفًا، أو منهجًا، أو مهارات، أو شروطًا، أو رسومًا، أو «بحث بالذكاء الاصطناعي»، أو صورة، أو تعليمات تفصيلية، أو حقول تحرير المحتوى. وعند وجود الاسم الإنجليزي الموثق يجوز عرضه كسطر ثانٍ تابع للاسم، دون اختلاق ترجمة. اسم المصدر الكامل، اسم الجامعة/المنحة، الرابط، وحالة الربط والقرار السابق تبقى متاحة **في تفاصيل مراجعة المرشح القابلة للفتح عند الطلب**، لا على وجه البطاقة.
6. **حالات العرض:** (أ) اسم + درجة مؤكدة؛ (ب) اسم + «الدرجة غير محددة»؛ (ج) ظهور المرشح في أكثر من درجة **بمرجع صريح لكل درجة**: بطاقتان/ملفا مستوى منفصلان أو مؤشرات مستقلة واضحة، لا تجمعها في هوية مستوى واحدة؛ (د) قائمة خالية: «لا توجد تخصصات غير مطابقة حاليًا»؛ (هـ) فشل التحميل: «تعذر تحميل المرشحين» + إعادة محاولة، وليس «لا توجد تخصصات».
7. **الصفحات/الفرز:** فرز خادمي بالأحدث ورودًا افتراضيًا، وصفحات أو «عرض المزيد» مع إجمالي صحيح. لا تكرر نفس المرشح في نفس الدرجة لأن جامعة أو منحة ثانية ذكرته؛ يبقى كل مصدر محفوظًا للمراجعة منفصلًا، دون حذف أي دليل.
8. **تفاصيل المراجعة الإدارية:** عند فتح المرشح تظهر مصادره الأصلية وأدلتها ودرجة الثقة/عدم الحسم إن كانت موثقة؛ مع الاستفادة من أدوات «المقارنة بتخصص موجود»، «ربط بالموجود»، «إنشاء هوية مسودة بعد الاعتماد»، و«رفض مع سبب» **الموجودة بالفعل**. اجعل هذه الإجراءات في مساحة/لوحة منفصلة عن القائمة المختصرة، مع احترام صلاحيات `admin:majors:review` وصلاحيات المالك الأصلية والضمانات الحالية، ولا تجعلها تُنفَّذ بالنقر على البطاقة مباشرة. **المراجعة أمر اختياري مستقل؛ مجرد عرض البطاقة لا يكتب في قاعدة البيانات.**
9. **مصدر الإدخال:** تلقائي من **علاقات التخصص غير المطابقة المخزنة فعليًا** في برامج الجامعات وأهداف المنح وشروط الأهلية المتعلقة بالتخصص، بعد التحقق من أن النوع مناسب؛ لا زر يجلب أسماء من الإنترنت، ولا مسح تلقائي للويب، ولا توليد تخصصات أو تفاصيل. أي نوع مصدر جديد لا يضاف إلا بعقد مالك وأدلة واستدعاء معتمد.

#### ج. ضوابط المطابقة وعدم التكرار — مهمة للغاية

- لا يكفي تطابق الاسم نصيًا أو الاسم المطبّع للحكم أن السجل «موجود» أو «جديد». التحقق يشمل الاسم العربي/الإنجليزي، الأسماء البديلة والمرادفات، الدرجة الصحيحة، والتصنيف المرجعي ومعرف Major/Profile الحقيقي. نتائج التشابه تُعرض **كاقتراح مراجعة** وليست ربطًا آليًا.
- لا يُفترض أن «أهداف منحة ما» تنطبق كلها على «كل درجات تلك المنحة». النموذج الحالي يجمع `ScholarshipDegreeTarget` الخاص بالمنحة مع مرشح هدف التخصص بصورة عامة؛ هذا **سياق درجات محتملة** لا يثبت زوج (تخصص + درجة) بعينه. إذا غاب دليل علاقة ثنائية محددة، تعرض «الدرجة غير محددة/تحتاج تحديدًا» أو قائمة درجات *محتملة* داخل المراجعة فقط؛ لا تختلق يقينًا ولا تولد تركيبات تخصص×درجة.
- تجمع المراجع متعددة المصدر **بعد تحديد الهوية والدرجة أو عند ثبوت التطابق**، ولا تبتلع نفس التسمية لدرجتين مختلفتين في صف واحد مبهم. إن كانت درجة أحد المراجع مجهولة، يُبقيها النظام مجهولة ولا يلحقها بغيرها لمجرد تشابه الاسم.
- احتفظ بـ`sourceDigest` أو ببصمة مصدر مكافئة وتحقق منها وقت القرار، مع المراجعة داخل معاملة/قفل و`revision` للموجود. إذا تغير المصدر أو تراجع عن الاسم، يُعاد تقييم المرشح ولا يُربط قديمًا. تحديث شكل مفتاح التجميع لا يجوز أن يفقد قرارات مراجعة أو أدلة محفوظة؛ جهّز توافقًا واختبارات ترحيل، ولا تُنفّذ هجرة متهورة.
- عند مطابقة التخصص الموجود تظل المواد القديمة والنسخ المعتمدة كما هي؛ قرار الربط لا يكتب فوق تفاصيلها. المصدر الأصلي للجامعة/المنحة يبقى ضمن سجل مالكه، ويُحدث رابط `majorId` فقط عبر Writer المالك بعد تحقق الحقوق وحالات التحرير.
- يُعامل المرجع الغامض أو المتعارض كمرشح «يحتاج تحقق» ولا يوصف «تخصصًا جديدًا مؤكدًا» قبل حكم المسؤول. المعروض في الصفحة **مرشح غير مطابق** لا دليل نهائي على عدم وجود التخصص عالميًا أو في قاعدة البيانات.

#### هـ. تعليمات تنفيذ Codex — المطلوب وما هو خارج النطاق

**نفّذ داخل `MajorAdminPage.tsx` و`NewMajorCandidatesPanel.tsx` والعقود والـAPI الضرورية فقط مع حفظ الكود الموجود، على فرع مستقل:**

1. اجعل زر «تخصصات جديدة» أعلى الصفحة يفتح واجهة اكتشاف مختصرة ذات **اسم + درجة** لكل مرشح. احتفظ بالعداد والبحث والفلتر والصفحات، مع تحديث العداد بعد التغييرات.
2. استخدم مالكي البيانات الحاليين ونموذج `NewMajorCandidate` وأداة المقارنة وWriter للجامعة/المنحة؛ **لا تنشئ مصدر حقيقة ثانٍ أو جدول Majors بديلًا**. صحح دلالة الدرجة والتجميع دون إضعاف بصمة المصدر أو الحماية من التكرار.
3. أبقِ أدوات المراجعة/الربط/الموافقة/الرفض القائمة في مساحة إدارية منفصلة وقابلة للفتح، **لا تُسقط وظائف موجودة** ولا تعرض نموذجًا طويلًا في كل بطاقة. لا تعامل قبول مرشح مسودة على أنه نشر؛ لا تنشئ تفاصيل أو اعتمادًا تلقائيًا.
4. أوضح للمستخدم الفرق بين **«مرشح جديد غير مطابق»** و**«تخصص معتمد»** في عنوان موجز فقط، لا رسالة ضخمة على الشاشة.
5. لا تبحث عن الأقسام، ولا تولّد تفاصيل، ولا تستدعِ ذكاءً اصطناعيًا أو الويب للبحث عنها، ولا تملأ محتوى الزمالات أو التخصصات الأربعة. **هذه المهمة تقع بالكامل على المالك لاحقًا.**
6. لا تغيّر تصميم بطاقة التخصص في «كل التخصصات» المحدد بالبند 05.19، ولا تسميات الكلية/المجال، ولا بقية أقسام الإدارة، ولا قوالب البكالوريوس/الماجستير/الدكتوراه/الزمالة. لا تغيّر دورة نشر Major.

**اختبارات القبول الإلزامية:** ظهور مرشح من برنامج جامعة، ومن هدف منحة، ومن شرط أهلية تخصصي فقط؛ عرض درجة مؤكدة أو غير معروفة بدقة؛ عدم تكرار مرشح واحد لنفس الدرجة بعد وروده من عدة مصادر؛ فصل الدرجات المتباينة حتى إن تطابق الاسم؛ عدم اختراع درجات من مجموع أهداف المنحة؛ اقتراح مرادف دون ربط آلي؛ ربط يدوي بهوية موجودة؛ رفض مع سبب؛ تبدّل `sourceDigest` أثناء القرار؛ صلاحيات المراجعة والمالكين؛ غياب API؛ عدد الشارة عند التحديث؛ البحث والفلترة بعدة صفحات؛ أسماء طويلة بالعربية/الإنجليزية؛ استجابة الهاتف وإمكانية الاستخدام بلوحة المفاتيح؛ عدم الكتابة أو النشر لمجرد فتح القسم. اختبر قواعد PostgreSQL في بيئة معزولة، وقدّم تقريرًا بنتائج التشغيل وأي ما يبقى ناقصًا؛ **لا تغيّر الإنتاج أو تدمج `main` تلقائيًا**.

**النتيجة المعتمدة:** «التخصصات الجديدة» = **قائمة تلقائية مختصرة لمرشحات التخصصات غير المحسومة: اسم + درجة موثقة، مع أدوات مراجعة بشرية موجودة خلف واجهة منفصلة**. **تفاصيل التخصص وأقسامه يكتبها المالك بنفسه فيما بعد.**
