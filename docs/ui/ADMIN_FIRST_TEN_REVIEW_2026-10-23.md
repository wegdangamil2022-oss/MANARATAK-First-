## اتصال البيانات منفصل عن التصميم

فحص مستقل مسجل الدخول، دون تعديل محتوى، أعاد:

- liveness: HTTP 200؛ الدول: HTTP 200، عددها 194.
- التخصصات: HTTP 200، عددها 3؛ الدورات والاختبارات والمحتوى: HTTP 200، عدد كل منها صفر في هذا الفحص.
- استغرق طلبا الجامعات والمنح أكثر من حد الفحص، 30 ثانية لكل طلب. ولم يُثبت سبب التأخر في هذه الدفعة.
- حتى بعض القراءات الناجحة استغرقت أكثر من مهلة مؤشرات Dashboard البالغة خمس ثوانٍ. هذا يفسر إمكان ظهور `TIMED_OUT` مع وجود اتصال بالقاعدة؛ لا يفسر تغير ترتيب الواجهة ولا يثبت أن كل أسباب التأخر معروفة.

إذن القاعدة متصلة، لكن استجابة قراءات بعض الأقسام تحتاج معالجة مستقلة. لم أرفع المهلة أو أختلق أرقامًا لإخفاء المشكلة، ولم أعدّ نجاح العرض نجاحًا لجميع واجهات API.

## التحقق

نجح TypeScript، والبناء الفعلي، وستة اختبارات مركزة: صلاحيات Dashboard والاحتفاظ بالدليل المتقادم، ومسح دليل المراجعة عند انتهاء الجلسة، والفرق بين العدد المجهول والصفر المتحقق، وربط بطاقة المراجعة بالفلتر القائم. صححت في محاولة أولى خطأً في أداة اختبار جديدة كانت تحاول تسلسل شجرة React الدائرية، ثم نجحت المجموعة. لم تُضعف assertions الموجودة.

ESLint للملفات المعدلة: صفر أخطاء و72 تحذيرًا، دون ادعاء أنها كلها جديدة أو قديمة. شملت التغييرات العرض فقط، ولم تتغير API أو Prisma أو migrations أو السياسات المالية. التشغيل المحلي يبقى تشخيصيًا للدخول والقراءة، والمهام الخلفية وكتابة المحتوى معلقتان.

الأدلة التفصيلية المحلية: `private/admin-first10-20261023/FIRST10_SOURCE_AUDIT.json` و`ACTUAL_READ_DIAGNOSTIC.json`. فُتحت الأقسام العشرة بالشبكة الفعلية على 1360×1000 و390×844 دون أخطاء JavaScript أو تمدد أفقي؛ اللقطات تشمل حالات تحميل ولا تثبت انتهاء كل القراءات. كشفت مراجعتها تكرار لوحة إنشاء المنحة فحُذف قبل التسليم. بقي التحقق المستهدف للحزمة النهائية في القسمين المتأثرين بهذا التصحيح.
